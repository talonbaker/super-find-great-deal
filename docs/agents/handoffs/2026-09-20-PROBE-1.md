## 2. The anomaly, before any scaling — the ranked suspects and the code path for each

The packet's first demand: *sleeping bodies should cost ~0, yet SHELF-1 measured 130 Resting props
→ server p95 5.8–6.7 ms at rest.* Ranked by expected size, each with the line that produces it.

### S1 — `Carryable._PhysicsProcess` writes four engine-side values per prop per tick, forever. **CONFIRMED BUG. FIXED.**

`scripts/game/sandbox/Carryable.cs:703-776` (at base). It is an `override` on the **body** of every
prop and it is not gated on anything — not on the server, not on being loose, not on being touched:

```
ApproachSpeedMps = LinearVelocity.Length();            // native read
...
_visual.Scale = _visualScale;                          // native write -> transform dirty -> RenderingServer
_material.EmissionEnergyMultiplier = Mathf.Lerp(...);  // native read + write -> RenderingServer.material_set_param
_outlineMesh.Visible = Highlighted && !IsHeld;         // native write -> RenderingServer.instance_set_visible
_thunkCooldown -= delta;
```

Four facts make this the primary suspect rather than a tidy-up:

- **The material is per-instance, deliberately.** `Carryable._Ready:395-396` —
  `_material = authoredMesh.MaterialOverride as StandardMaterial3D ?? new StandardMaterial3D();
  authoredMesh.MaterialOverride = _material; // the highlight/pop pulse below mutates this exact
  instance`. So it is N distinct material-parameter writes a tick, not one shared one.
- **Neither write is idempotent at the engine boundary.** Godot's `Node3D::set_scale` propagates a
  transform change unconditionally; `set_emission_energy_multiplier` calls
  `material_set_param` unconditionally. Writing the value a node already has is not free.
- **Both targets are asymptotic and never arrive.** The emission is
  `Mathf.Lerp(current, target, 10*dt)`, so the "settled" case writes forever.
- **It runs on every peer**, so it is the one suspect that explains the server number and the
  client number with the same sentence.

Per Resting prop per tick, on every peer: **2 native→managed `_PhysicsProcess` callbacks**
(`NetworkedProp` + `Carryable`, both overrides) **and ~7 native property accesses, 3 of them
reaching the RenderingServer.** At 130 props that is ~1 000 boundary crossings a tick, 60 000 a
second. At 2 000 it is ~16 000 a tick, **just under a million a second**, for props nobody has
touched.

**Fix** (commit `29fb5d6`): `CarryIdle.IsSettled` + an early-out. Measured saving in §5.

### S2 — the server's per-tick loop walks every prop to discover there is no work. **CONFIRMED. FIXED.**

`scripts/game/props/PropManager.cs:638-649` (at base):

```
foreach (PropState p in _registry.All)
{
    if (p.Mode == PropMode.Loose) _loosePropsScratch.Add(p);
    else { _looseSettle.Remove(p.Id); _lastStreamed.Remove(p.Id); }
}
if (_loosePropsScratch.Count == 0) return;
```

Its own comment three lines above says *"the common case is zero loose props on most ticks"*, and
the room is asleep for almost all of a round — so this is O(props) work, 60 times a second, to
learn there is none. Two dictionary `Remove` calls per non-Loose prop on top.

**And it allocates.** `PropRegistry.All` is typed `IReadOnlyCollection<PropState>`
(`scripts/net/PropRegistry.cs:22`), so `foreach` over it boxes a `Dictionary.ValueCollection`
enumerator on the heap **every tick**, and `PropState` is a `readonly record struct` carrying a
`Transform3D` (~64 bytes) which is copied through the interface enumerator per element. At 2 000
props that is 120 000 struct copies a second plus 60 gen-0 allocations a second from this loop
alone. Server-only, so it explains the server half and not the client half.

**Fix** (commit `29fb5d6`): `PropRegistry.LooseCount`, maintained on every transition inside the
store, plus `AllValues` typed concretely so the hot `foreach` uses the struct enumerator. Measured
saving in §5.

### S3 — frozen-kinematic Resting bodies may never enter physics sleep

`NetworkedProp._Ready:145-148` puts **every** prop, on every peer, into
`Freeze = true; FreezeMode = Kinematic`. A Godot kinematic body is not a static body: it is kept in
the physics server's active set (it has to be, because a kinematic body's velocity is derived from
transform changes), so 130 resting props may be 130 bodies the solver integrates and broadphases
every step, each holding a persistent contact manifold against the shelf board it stands on.

**This one is measured directly rather than argued**: the probe now samples
`Performance.Monitor.Physics3DActiveObjects`, `Physics3DCollisionPairs` and `Physics3DIslandCount`
every tick. *(Verdict and numbers in §5.)* If active bodies ≈ the prop count, S3 is real and the
candidate fix is `FreezeMode.Static` for Resting — **not taken blind**, because a static-frozen body
changes what `DropOffBin.ScanServer`'s `Area3D.GetOverlappingBodies` poll sees, and that poll is the
round's end condition and the trigger for the whole startle (survey R2). Any such change needs
`Run-BurstDoorTest` and the bin's own suite behind it, which is a packet, not a line.

### S4 — the tail is the machine, not the props

SHELF-1's at-rest rows are p50 **1.48 ms**, p95 **5.80 ms**, peak **20.42 ms** — a 14× gap between
p95 and peak **on an idle room**, which is the shape of a collection or a scheduler slice rather
than of per-prop work. Two prior facts point the same way:

- SHELF-1 states plainly that *"the machine was not idle for either"* of its at-rest runs.
- **STOCK-1 §5.4 measured 2 212 extra objects making every column BETTER** (p50 1.958 → 1.634,
  p95 7.055 → 6.483) and said so: *"the difference is machine noise and the noise is larger than
  the effect."*

So the honest discriminator for the whole packet is **the slope against N, read off p50**, not the
absolute p95. The probe reports GC collections and bytes allocated over the window so this can be
separated rather than asserted. *(Verdict in §5.)*

### S5 — the instrument was measuring itself

`ReachCostProbe._PhysicsProcess` counted the population by walking `PropManager.LiveProps` **every
tick**. `LiveProps` is a C# iterator (allocates a state machine per call) whose body does one
dictionary lookup and one `IsInstanceValid` interop call per prop. Free at 130; **120 000 lookups
and 120 000 interop calls a second at 2 000**, inside the loop measuring how expensive the tick is.
Counted once after the warm-up now. Not a shipped bug — a rig bug, and it would have inflated
exactly the rows this packet exists to produce.

## 3. How the population is staged, and the one thing that is not shippable about it

`--probe-props N` seeds N props through `ServerSpawn` at world build, before any client connects.
`ProbeSeedLayout` is the geometry, engine-free and pinned by `ProbeSeedLayoutTests`:

- **Walkway floor only.** SHELF-1's arithmetic is 4 bays × 0.5 m + 5 walkways × 1.6 m = the room's
  10 m width exactly, so a band ±0.6 m about a walkway centre cannot touch a bay. The boards
  themselves are full — 120 facings plus STOCK-1's filler in every cell a facing does not stand in
  — so a seeded prop there would be born inside static geometry, which is STOCK-1 §4.4's whole
  lesson (`StaticOverlap`, `InsideStatic`, `NobodyCouldReachThat`, in a room that renders perfectly).
- **x ∈ [−4.4, 4.4]**, inside the bays' span, so nothing lands in a cross-aisle, on the pillar at
  (6, 1, 2.5), or on `SearchSpawn_0/_1` at x = ±4.5.
- **z = 0 is left empty.** That is the lane the measured bot walks and looks down.
- **0.24 m pitch**, against the widest seeded prop's 0.199 m plan diagonal — 41 mm, twice
  `PlacementIntegrity.DefaultOverlapToleranceM`.
- **Kinds cycle Can / Box / Produce** so every row carries all three of SFX-1's material voices and
  all three collider shapes.
- **Fill order is a prefix**: the row at N = 130 is the first 130 slots of the row at N = 2000.
  Pinned by a test, because without it no two rows of §4 are the same experiment.
- Every seeded prop is then run through the shipped layer 2 (`ServerAuditRest`) and the burst is
  timed — see §6.

**The one thing that is not shippable, stated rather than hidden:** one floor layer holds **888**
slots, so N = 1000 is two layers and N = 2000 is three, at 0.32 m spacing. A Resting prop is a
frozen kinematic body, so a slot 0.32 m up holds it perfectly still — physically fine, visually a
shelf's worth of product hanging in a walkway. The top layer sits at 0.64 m, under the 1.040 m
eyeline REACH-1 measured, so the N = 2000 capture photographs the room rather than a wall.
**This probe measures BODY COUNT. STOCK-2 is the lane that turns a number into stock on a shelf**,
and its instances go where STOCK-1's bake already knows how to put them.

Two further deviations from the packet's method, both deliberate:

- **The packet says "seeds N extra Resting props of the three material prefabs".** A runtime-spawned
  prop goes through `PropManager.SpawnFromData`, which builds a bare `NetworkedProp` whose
  `Carryable` is **code-built** (`Carryable.BuildShape`) rather than an instance of
  `Can.tscn`/`CerealBox.tscn`/`Produce.tscn`. Same `PropKind`, same collider, same mass, same
  material voice, same per-tick cost — but the MESH is the code-built one at Godot's default
  tessellation (`CylinderMesh` 64 radial, `SphereMesh` 64×32). For the physics and interop columns
  that is identical; for the **render** columns it is an upper bound, and it is the right direction
  for a bound. Changing `SpawnFromData` to instance a prefab would change the spawn payload every
  peer parses, which is not a probe's business.
- **The wave is capped at 100** (`--cost-shove-count 100`) at every N, per the packet. SHELF-1's and
  REACH-1's waves were "every prop in the room", which is a fixed experiment only while the room
  holds a fixed number of props. **So §4's wave column is NOT comparable to SHELF-1 §7.1's wave
  rows** — those knocked all 130 loose; these knock 100 loose at every N. The at-rest column IS
  comparable, and that is the one the 8 ms bar is on.
