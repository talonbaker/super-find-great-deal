## 0. The diagnosis, in three sentences

**Godot renders on the RTX 4070 and Windows presents on the Intel UHD 770, and every frame has to
cross between them.** `nvidia-smi` reports the 4070's `display_active` as **Disabled** — no monitor
is attached to the discrete card at all — while `Win32_VideoController` gives the Intel UHD 770 the
only `VideoModeDescription` on the machine; Godot's own boot line says
`Using Device #0: NVIDIA - NVIDIA GeForce RTX 4070`, because Godot 4 picks the discrete adapter by
default and nothing in this project overrides it. **One flag moves the render to the adapter that
owns the screen and the stall disappears entirely**: `--gpu-index 1` takes the windowed client from
**255.851 ms** median frame time to **2.837 ms**, and from **269 stalls** in the window to **zero**,
with no other change to the build.

**It is not GC, not vsync, not the rendering method and not the driver API.** The instrument this
lane added records `GC.CollectionCount` per frame, and across **52 stall frames** in the cleanest
reproduction **not one** had a collection on it (`with_gc=0`). Vulkan, D3D12 and OpenGL on the
NVIDIA all stall; `forward_plus` and `mobile` on the NVIDIA both stall; vsync on and vsync off on
the NVIDIA both stall. The single variable that removes it is which adapter draws.

## 2. The instrument

`CameraPacingProbe` is SICK-1's, unchanged in what it measures. Four columns were added because
SICK-1 could not tell three candidate mechanisms apart and nothing in the CSV could:

| column | what it rules in or out |
|---|---|
| `gc0` / `gc1` / `gc2` | `System.GC.CollectionCount` per frame. A managed pause steps a generation counter on **exactly** the stall frame. |
| `phys_ticks` | physics ticks run for this render frame. **8** is `max_physics_steps_per_frame` catching up after a frame the engine lost; **1 with a huge `phys_proc_ms`** is the opposite finding — a physics blow-up. |
| `proc_ms`, `phys_proc_ms` | `TimeProcess` / `TimePhysicsProcess`. **NOT per-frame — a per-second maximum; see §3.4, which is a correction this lane owes three other handoffs.** Read as "the worst idle step in this frame's second", they separate the draw from the simulation. |

All four are single cheap reads of values the engine has already computed for the frame that just
ended, so the rig's own cost does not move the number it reports — the objection `ReachCostProbe`'s
header makes about always-on instruments.

Plus `[adapter]`, printed once per measured run (§1.2). **A pacing row taken on a different adapter
than the row beside it is not comparable to it, and until this line existed no log in this repo said
which adapter a row was taken on** — which is exactly how SICK-1, HANDS-1 and STOCK-1 each recorded
this stall and none could name it.

| thing | where |
|---|---|
| the four columns, `[adapter]`, `[stall]` | `scripts/game/sandbox/CameraPacingProbe.cs` |
| the driver (engine flags, focus, repeat) | `tests/Measure-RenderStall.ps1`, **unregistered**, **udp/7914** |
| the histogram capture | `tests/Show-StallHistogram.ps1` |
| the raw data | `docs/qa/2026-09-21-stall-1/*.csv` — one row per render frame |
| the histograms | `docs/qa/2026-09-21-stall-1/histograms.txt` |

**`Measure-RenderStall.ps1` is a second driver rather than an edit to `Measure-CameraPacing.ps1`,
which stays byte-for-byte what SICK-1's handoff measured** (the packet says to reproduce with it
unchanged, and row 1 of the table below was taken with it). It adds the three things that script
structurally cannot do:

- **`-EngineArgs` (the `|` in a config string).** `--gpu-index`, `--rendering-driver` and
  `--rendering-method` are **engine** flags and go BEFORE the bare `--`.
  `Measure-CameraPacing.ps1` appends every extra argument AFTER it, where the engine never sees
  them — so without this the packet's three central rows cannot be built at all.
- **`-Foreground`.** SICK-1's client was an UNFOCUSED background window; Talon plays focused.
- **`-Repeat`.**

**`-Foreground`'s first version silently measured three unfocused rows and labelled them
focused**, and that is worth the line it costs. `tests/_Common.ps1` resolves Godot to the
`_console` wrapper, which spawns the real engine as a **child**; `Process.MainWindowHandle` on the
object `Start-Process` returns is therefore always zero. It now enumerates every visible top-level
window in the launched process tree, and it **reads the foreground pid back** after the call rather
than trusting it — Boot.cs's own rule for window mode ("the read-back, not the intent"), which is
the only reason the mislabelling was caught instead of shipped into this table.

### 3.3 What a stall frame WAS — the three columns that name the mechanism

Across every NVIDIA row, on the stall frames:

- **`8-tick` ≈ `stalls`** (268/269, 244/244, 52/52, 43/43). Every stall frame ran the full eight

  This is the column that says "render", and the packet's proposed

- **`gc` is 0 on the two clean high-frame-rate rows** (row 8: 0 of 52; the focused repeat: 0 of 43)

- **`proc_ms` says the stall is in the idle step, and `phys_proc_ms` says it is not the

### 3.4 A correction this lane owes the repo: `TimeProcess` is a PER-SECOND MAXIMUM

**`Performance.Monitor.TimeProcess` and `TimePhysicsProcess` are not per-frame values.** This lane
added them to the CSV believing they were, and the data said otherwise before any of it reached a
table:

| run | recorded frames | **distinct `proc_ms` values** | window |
|---|---|---|---|
| `gpu1-novsync` | 11 055 | **37** | 35.9 s |
| `novsync-nvidia` | 48 780 | **56** | 54.6 s |

**One new value per second**, and the value each second holds is the WORST idle step in that second,
not the mean and not that frame's. That is why `novsync-nvidia` shows a mean `frame_ms` of 1.12 ms
beside a mean `proc_ms` of **430.79 ms** without either number being wrong, and why the Intel row's
`proc_ms` maximum is **800.6 ms** on a run whose worst frame was **69.9 ms** (that 800.6 is the boot
second).

Read that way they still carry the finding, and carry it well:

| | `proc_ms` mean (per-second max) | `phys_proc_ms` mean (per-second max) |
|---|---|---|
| NVIDIA 4070, vsync off | **430.79 ms** | 4.76 ms |
| Intel UHD 770, vsync off | **9.34 ms** | 5.17 ms |

Godot's idle step is where `RenderingServer::draw()` is called from, so a per-second worst of
~500 ms on one adapter and ~9 ms on the other localises the half-second to the draw — while
`phys_proc_ms`, measured identically, sits at **4.76 vs 5.17 ms**, which is the control that says
the simulation is the same on both sides and the difference is not it.

**This matters beyond this lane.** `PerfHud.cs` prints `TimeProcess` as `frame_ms`, and SHELF-1's
and STOCK-1's `pms` is `TimePhysicsProcess` described as "a 5 Hz spot reading". On this measurement
both are **per-second maxima**, so every number quoted from them is an upper bound over a second
rather than a sample of a frame. The comparisons those handoffs draw are between like and like and
so survive; the absolute values should be read as worst-in-second. The evidence is in the class doc
of `CameraPacingProbe` and it is an entry `.claude/rules/test-suite.md` should carry — §12.

## 4. So what is it, in plain words

**A cross-adapter present.** The RTX 4070 draws the frame into its own video memory. Nothing of the
4070 is on the screen, so Windows must copy that frame across the PCIe bus into memory the Intel UHD
770 can scan out, and the Intel's display controller presents it. That copy is the ~510 ms nobody
could find, and it is invisible to every instrument that looks inside the engine — which is why
three lanes in a row measured this stall and none of them could name it.

**Why it is periodic rather than constant with vsync off**: with `--vsync 0` Godot presents in
immediate mode and the driver is free to drop frames, so almost every frame skips the copy
altogether (0.452 ms) and the copy's true cost only lands when one is actually taken. With vsync on,
every frame must be copied and presented, so the cost stops being a spike and becomes the frame
time — which is the 255 ms rows, and which is why the machine is at 4 fps today.

- **NO KNOB DEFAULT MOVED. Not one.** The table justifies no code change, and the reason is worth
  saying plainly: **the fix for this machine is a cable, and a default that forced every player onto
  their integrated GPU would be a catastrophe for every player whose monitor is plugged in
  properly.** `--gpu-index` is a stock Godot engine flag and already reachable without a rebuild, so
  there is nothing to add for Talon to use the workaround either. §7 is the ride-card line.
- **`max_physics_steps_per_frame` 8 → 4 was not run**, and the packet's own reason for wanting it is
  already answered by a column. That row exists to tell render from physics; `phys_ticks` tells it
  directly, on **every** stall frame of **every** row, rather than by inference from one more
  32-minute batch. Moving it would also have been moving a knob default the table does not justify,
  which the gates forbid.
- **Fullscreen / borderless was not run.** `Boot.cs`'s own comment records that a suite taking the
  one display on this shared machine "has already broken the verification of every other packet in
  the wave", and PHYS-2 was live throughout. It also cannot change the finding: the 4070 has no
  display attached, so a fullscreen window is still on the Intel's screen and still has to be copied
  there. Stated rather than smuggled — it is the one row of the packet's list that is missing.
- **A scene with STOCK-1's bulk versus the base scene was not run.** The stall is measured at
  `draws=11..12, objs=112..114` — a nearly empty holding room — and is 500 ms. Scene cost is not in
  the same universe as the effect, and STOCK-1 already measured the bulk's true render cost (six
  more draw calls).
- **`Measure-CameraPacing.ps1` was not edited.** Row 1 of the table is that script, unchanged, so
  SICK-1's rig and its handoff still measure what that handoff says they measure.
- **Nothing in `project.godot` was touched**, and `physics/common/max_physics_steps_per_frame` is
  still absent from it (Godot strips settings that match the default; the `[adapter]` line prints
  the live value, **8**, so the absence is now evidenced rather than assumed).
