## 1. Layer 2 — the rest audit

### What CARRY-1 left and what this adds

CARRY-1 shipped the RECORDING half on purpose: on a settle it ran `PlacementIntegrity.Check` and,
if the pose passed, wrote it to `NetworkedProp.LastGoodTransform`; if it failed it logged one line
and left the prop where physics put it. Its own comment named this lane as the owner of the
correction, and said why the two halves had to ship together: *"a prop teleporting with no audit
behind it is indistinguishable from a desync."*

So the correction and its log line landed in the same commit. The failure path, in the order §5b
gives:

1. **Depenetrate** along the minimum translation — `GetRestInfo`'s normal, `CollideShape`'s depth
   — up to `DepenetrateMaxM` (0.15 m), re-checking after each push, up to three pushes so a prop
   wedged in a corner (inside two things) can clear both. The total distance is still capped.
2. **Otherwise home to `LastGoodTransform`**, never to spawn.
3. **And check that too.** A prop that was authored or seeded inside the scenery has a last-good
   that is itself illegal; reporting "restored" about that would be a lie the round then trips
   over at Confirm. That case is `Outcome.Stuck`, it logs a `GD.PushWarning`, and it is what
   layer 3 refuses on.

### One implementation, three callers

The whole latch body lives in `PropManager.ServerAuditRest`. The settle branch of
`_PhysicsProcess` calls it; the planted self-test calls it on an authored pose; §5b layer 3's
precondition ("the target must be Resting **and must pass layer 2**") calls it on the Confirm
press. Two implementations of "may this prop stay here" would be two answers to one question —
the argument `PlacementIntegrity`'s own header already makes about layer 1 — and the second is
the one nobody would maintain.

`ServerAuditRest` refuses to run on a HELD prop. That is not tidiness: the correction ends in
`SettleToRest`, which unbinds a prop from its holder, so auditing something in somebody's hands
would take it out of them — and the one caller that can reach that case (the Confirm-time
precondition, on a hider who has not put the object down) is exactly the one the round is about
to refuse for a different reason.

### The kill plane now recovers to last-good, not to home

`NetProfile.KillPlaneY` is −30. The pre-REACH-1 branch teleported an out-of-bounds prop to
`HomeTransform`, which for an authored prop is **where the level put it** — so a hider who hid the
target in the far aisle and then watched a seeker knock it off a ledge would have watched the game
hand it back to its starting shelf. It now goes to `LastGoodTransform`.

**This moves nothing in the existing suites and that is checkable rather than hoped.**
`NetworkedProp.Init`/`InitAuthored` seed last-good from the spawn pose, and a prop only updates it
on an audit that PASSED. `Run-ThrowTest`'s prop 3 is spawned, grabbed, thrown and goes out of
bounds without ever latching Resting in between, so its last-good is still its home and the
suite's `(2, 0.5, 30.5)` assertion is unchanged. It passed in the marathon (§5).

### The one defect this lane's own test found

`PropRegistry.Release` refuses anything that is not HELD — correct for the drop/throw verb it is,
and the reason `ServerNudgeLoose` initially did nothing to the registry while still unfreezing the
body. The planted faller therefore fell forever: 179 m down after 10 s, with the kill-plane branch
never reached because the prop was never `Loose` in the registry. Fixed with
`PropRegistry.SetLoose`, the explicit sibling of `SetResting`, used only by the dev nudge; `Release`
keeps its rule.

## 2. Layer 3 — grab-reachability

### The rule, and why it is arithmetic

`Reachability.Evaluate` is engine-free over `IReachSampler`, which an adapter fills with physics
queries. Everything that DECIDES — how many points, where, which hit counts, what the refusal is
called — is `dotnet test`-able without an engine, a world or a server. The engine half
(`PhysicsReachSampler`) is three query kinds and no judgement.

- **24 candidate standing points:** 12 at `GrabReachM` (2.4 m), 12 at half that, generated at the
  TARGET's own height. Wide ring first, because that is the commoner win and the loop returns on
  the first point that counts.
- **A point is standable** when a downward ray from it finds static floor within
  `FloorProbeM` (1.5 m) with an up-facing normal, AND a player capsule fits standing on it.
- **From that point's eye height**, a ray at the target's centre and a ray at the top of its
  bounds. The point counts if either meets the target, a movable prop, or nothing at all.
- **Reachable ⇔ at least one point counts.**

Refusal precedence is load-bearing: `InsideStatic` (layer 2 also failed) short-circuits before
anything is sampled; `NoStandingPoint` outranks `OccludedByStatic`. "There is nowhere to stand"
tells the hider to move it DOWN and "the scenery is in the way" tells them to move it OUT, and
handing them the wrong instruction is how a 30-second hiding phase gets spent fighting the game.

### Two exclusion sets, and each is a decision

- **The floor probe and the body-fit cast exclude every avatar AND every prop**, so only STATIC
  geometry can create or deny a standing point. A seeker does not have to be able to stand on a
  crate for a hide to be fair, and a crate sitting where they would stand is a crate they move.
- **The eye ray excludes avatars only.** Props are what it is there to see: a first hit on a bin
  or a box COUNTS. Excluding the other player's body is the rule `PlacementIntegrity` already
  applies for the same reason.

### `ReachVerdict.Winner`, and why it was added after the first green run

The first planted run reported the bin and the box cases reachable with `pts=1/1of1` — and that
boolean could not tell "reachable because the seeker has a clear line to the crate" from
"reachable because the bin on top of it is something they can move". A room where the bin was
never authored would have passed both cases. `Winner` carries what the winning ray met first, the
self-test asserts `MovableProp` on those two, and the verdict lines now print `firstHit=`.

### The probe body is the LIVE avatar when there is one

`PhysicsReachSampler` measures the capsule off a live `SandboxAvatar` when one exists and falls
back to the reference figure otherwise, and it says which in the log line. The two differ a lot:
`live avatar r=0.145 h=1.200 eye=1.040` against `reference figure r=0.360 h=1.241 eye=0.995`. The
planted self-test (no players) therefore runs the STRICTER body — a wider capsule fits in fewer
places — which is the safe direction, and the live audit runs the body that actually has to fit.
**Worth knowing before reading a disagreement between the two as a bug.**

## 3. How the fact reaches the round

`ReachabilityFactSource` implements `IRoundFactSource` and answers only `TargetRetrievable`;
everything else is the resting value. It is registered **first among the real sources** on the
server, which matters because `RoundFacts.Combine` takes the first NON-NULL answer in registration
order.

**It answers `null` until it has measured something**, and that is the contract rather than a gap.
With no target — every suite that does not pass `--reach-target`, and the whole holding room — it
stays null, the loop reads all-null as retrievable, and nothing that existed before this branch
changes behaviour by one byte. A source that guessed `false` before measuring would refuse every
Confirm in the program; one that guessed `true` would be a layer that silently does nothing.

### The Confirm-time re-measure needed one new seam

§5b says the audit runs "when the target latches Resting and once more on the Confirm press; never
every tick". The first half is `PropManager.RestLatched`. The second had nowhere to hang: a fact
source cannot see another source's press, and `HideSeekDriver` collected the facts once and
stepped.

`IConfirmTimeAudit` is that seam — an **optional side interface**, not a member of
`IRoundFactSource`, because BTN-1, TASK-1 and the dev script all answer instantly from a latch and
putting an empty method on all of them would be four implementations of "no" so that one lane
could say "yes". The driver collects the facts, and **if and only if** `HiderPressedConfirm` is
set, calls every implementer and collects again, so the value the loop refuses on is the one
measured on the press. Two `Combine` calls on a Confirm tick; one on every other tick.

Without it, the hider could set the object down legally, shoulder it into a shelf back on the way
out, and press Confirm on a fact measured before the shove. Planted fault B (§4) is exactly that
seam removed, and it lets a crate buried inside the pillar start the seek.

### The loud line for the case the design must never hit

§5b: layer 2 keeps running during Seeking. When the target latches Resting during Seeking and
layer 3 then fails at the corrected/last-good transform, `ReachabilityFactSource` emits
`GD.PushWarning` **and** a print carrying the packet's exact string:

```
REACH-1 target unreachable during Seeking
```

There is no rescue beyond the audit in the MVP, so what this can do is make the event impossible
to miss. A playtest proves the design did NOT hit it by grepping for that sentence and finding
nothing.

## 6. Decisions a reviewer should check rather than take on trust

### No second refusal enum value

The packet said to append one if the six cases need distinct sentences. **They do not.** All three
layer-3 reasons and both layer-2 stuck reasons reach the player as one sentence — *"NOBODY COULD
REACH THAT — MOVE IT"* — and the hider needs "move it", not a physics tutorial. The distinctions
that matter (`InsideStatic` vs `NoStandingPoint` vs `OccludedByStatic`) are in the server log and
in `ReachVerdict.Sentence`, ready for BTN-1 or the HUD strip to show a more specific line without
a new wire byte. `HideSeekRefusal` is unchanged, so no stale peer can render a sentence the server
did not refuse with.

### A prop born inside the scenery keeps a bad last-good, deliberately

`NetworkedProp.Init` seeds `LastGoodTransform` from the spawn pose whether or not that pose is
legal, so a crate seeded inside the pillar has nowhere good to fall back to. That is **not** a bug
to fix by validating at spawn: §5b's fallback is "the last good transform, never spawn", and a
prop that has never had a good transform is precisely the case layer 3 is the backstop for. It is
also what makes the two-bot smoke honest — the refusal comes from the audit chain doing its job
and failing, not from a check that was skipped.

### `PlacementIntegrity` still measures a prop by its FIRST collider

CARRY-1's choice, unchanged here, and it now has a live consumer that is multi-shape: the bin and
the box each have five or six box colliders and are audited by their lid alone. That is fine for a
fixture that is scenery rather than a subject, and it is written into both scene headers. **The
day a real multi-shape prop ships, that is the line that has to change** — and the change is a
query per shape on a path that runs once per settle for every prop in the room, which is why
CARRY-1 did not pay it up front.

### Blocker classification uses one `IntersectShape` hit

`StaticOverlap` vs `PropOverlap` is decided from the single collider the refusal-path
`IntersectShape` names, which need not be the body that produced the DEEPEST contact `CollideShape`
measured. Pre-existing imprecision (CARRY-1 named the blocker the same way); it affects only which
of two log words is printed, never whether the audit acts. Left alone rather than paid for on the
hot path.

```

                 its own state — a rest latch, a correction, a boolean the round loop refuses
                 on — with no player acting on it directly. LEVEL because the planted room is
                 an authored space and because the audit's whole subject is whether a level's
                 geometry has swallowed an object. INTERACTION deliberately NOT applied: no
                 player presses anything new here. The verb this fact gates (Confirm) is
                 BTN-1's, and INTERACTION's §2/§3 "a refusal must say why" is satisfied
                 upstream by ROUND-1's named refusal, which this lane feeds rather than adds to.

Items checked:   MECHANICS §1 (boundary conditions) — the three thresholds are explicit and
                 named: PlaceOverlapToleranceM 0.02 m is inclusive (`deepest <= tolerance`
                 passes), DepenetrateMaxM 0.15 m is the TOTAL of up to three pushes and is
                 checked before each, and FloorProbeM 1.5 m is measured from the target's own
                 height, not the floor's.
                 MECHANICS §3 (simultaneous events) — the Confirm tick is the one place two
                 systems could disagree about the same object. Resolved by a fixed order that
                 is stated in code: layer 2 first, then layer 3, then the loop, with the facts
                 re-collected in between so the loop cannot read a value measured before the
                 audit. Nothing depends on which node's _PhysicsProcess runs first.
                 MECHANICS §4 (idempotency) — a second ServerAuditRest on an unchanged prop is
                 a no-op that re-broadcasts the same Resting transform, which the funnel already
                 documents as harmless; and the audit is refused outright on a HELD prop, which
                 is the one way a repeat call could have done damage (it would have emptied the
                 holder's hands).
                 MECHANICS §7 (end conditions) — the Hiding buzzer and a pressed Confirm can
```

## 8. Open for the orchestrator

- **`--reach-target` is a stopgap and BTN-1 should replace it.** `ReachabilityFactSource.TargetPropId`
  is a settable property; BTN-1's `ObjectRack` should set it when the hider takes an object off the
  rack, and set it to −1 on the reset edge. Until then the fact is null in a real session and
  layer 3 does nothing, which is the safe default but is not the shipped game.
- **SHELF-1 will move two numbers in this branch.** The cost phase's population assertion is "at
  least the 150 seeded", and a hundred authored shelf props land in the same room; and
  `SearchRoom.tscn`'s `SearchPillar` (which phase 2 buries its target in) is explicitly marked as
  deletable by SHELF-1 — if it goes, phase 2 needs another interior static block, and the pillar's
  own header already says to leave a replacement.
- **Nobody has set a server frame-time budget for this game.** Phase 4 measures and reports; it
  asserts only that the measurement had the right population and that the props actually settled.
  Inventing a budget here would be a number nobody agreed to. p50 2.8 ms / p95 20.3 ms with 150
  props in a shove wave is the first datum.

  the system working, or the cost fixture does not produce the overlaps a real room will. SHELF-1's
  aisles, where a knocked crate has somewhere to wedge, are the first honest test of that.
