## Rename

`config/name` is what drives `user://`, and `user://` resolves by project NAME — so every checkout
of a project on a machine shares one profile directory. Leaving it as "Watis World" would have put
this game's suites and bots inside Talon's live Watis profile; a suite bot has already spent a real
achievement into that one once.

The protocol bump and the lobby tag are the two halves of one fence. The tag stops a Watis room
code resolving to this game's lobby while both develop against Spacewar; the version stops a Watis
client direct-connecting to this server over ENet, where no lobby tag can reach. Nothing on the
wire changed shape — the bump is spent entirely on refusal.

**Renames, exhaustively:** `WatisWorld.csproj` → `SuperFindGreatDeal.csproj`, `WatisWorld.sln` →
`SuperFindGreatDeal.sln`, and their references in `tests/_Common.ps1`,
`tests/Run-MultiplayerTest.ps1`, `.github/workflows/build.yml`,
`tests/unit/SailNet.Tests.csproj`'s `ProjectReference`, and the two UI tests that find the repo
root by walking up until they see the csproj by name.

**`tests/unit/SailNet.Tests.csproj` KEPT its name deliberately.** The packet enumerated two files
to rename and told the lane not to rename namespaces or identifiers; renaming the test project is
a `RootNamespace` change. Step 5 of the packet says `dotnet test tests/unit/<renamed>.csproj` — the
command is `dotnet test tests/unit/SailNet.Tests.csproj`, unchanged. It is on the backlog.

## The world

```
scenes/game/world/supermarket/
  Supermarket.tscn    the seam: instances the three rooms and authors no geometry of its own
  HoldingRoom.tscn    10 x 10 x 3.5 m   HoldingSpawn_0..3   at x = 0
  SearchRoom.tscn     14 x 10 x 3.5 m   SearchSpawn_0..1    at x = 40
  TaskRoom.tscn       10 x 10 x 3.5 m   TaskSpawn_0..3      at x = 80
                      + a 3 x 3 x 3.5 m vestibule, Vestibule_0, behind the main room's +Z wall
```

Interior floor at y = 0, ceiling underside at y = 3.5, slabs and walls 0.4 m thick and overlapping
at the corners. One `OmniLight3D` per room, a different flat grey per room so a capture says which
room it is without a caption. Every `StaticBody3D` carries one `BoxShape3D` and one `BoxMesh` of
the same size.

**40 m apart is load-bearing, not spacing.** Proximity voice cuts off at 24 m, so the separation is
what makes "the hider cannot hear the seeker through the wall" a property of the geometry rather
than of a gate somebody could switch off. `VoiceProximityGate.DefaultForWorld` is on for this
world for the same reason. The self-test asserts a 30 m floor between rooms — the design property,
not the layout's current value.

**`TaskRoom.tscn`'s `WallZPos` is the door that is not a door yet.** DOOR-1 replaces that node —
the main room's +Z wall, the one `Vestibule_0` faces. It is deliberately a full wall and not a
doorway with a leaf in it: a hider who can see a gap has been told where the ending comes from.

`SupermarketWorld.SpawnPoints` is the holding room's four markers and only those.
`SpawnPointsFor("search" | "task" | "vestibule")` reaches the rest by name — those are teleport
destinations, not spawns, and must not be mixed into the default array.

**`scripts/game/world/RoomTeleport.cs`** is new: the epoch-bump teleport lifted out of the deleted
`TvPortalHost`, with its per-peer cooldown, deliberately separated from what triggers it. Nothing
calls it. ROUND-1 does, from the server's phase-transition tick.

### 4. Two-bot replication, on the real world

```
powershell -File tests/Run-MultiplayerTest.ps1 -BotCount 2
PASS: 2 bots, 4 observer/subject pairs checked, max position error 0.000m (tolerance 0.75m).
```

`Run-MultiplayerTest.ps1` now defaults to `--world supermarket` (`-World open` still reaches the
CI slab). Two consequences, both measured, both in the script's own header:

- **Assertion 3 was net displacement from spawn and is now PATH LENGTH.** The deterministic bot
  brain walks radially outward from the world origin; on a 64 m slab it covers 15 m, in a
  10 × 10 m room it walks into a corner. Path length asks the question the assertion actually
  means — is this live replicated data or the spawn packet echoed back — without being a statement
  about the size of the room.
- **The bar is per world:** 5.0 m on `open`, 2.0 m elsewhere. Both bots walk 3.33 m in the holding
  room, repeatably. 2.0 m is two orders of magnitude above prediction jitter.


It gates on that SUMMARY line, not on the exit code: a process that dies before printing it exits
non-zero for reasons that have nothing to do with the level, and "never reported" and "reported a
failure" are different problems with different fixes. The exit code is checked after the line.

**The first fault plant did not fail, and that is the useful part.** Renaming `HoldingSpawn_3` to
`HoldingSpawn_9` left the suite GREEN — a count check cannot see a renumbering, and the numbering
IS the contract, because these markers are sorted by the number in the name to fix spawn order
across peers and `Gameplay.SpawnPlayer` indexes that array by join order. The check now requires
`0..n-1` exactly. The same rename then failed on the right line
(`room 'holding' numbers its markers [0, 1, 2, 9]; the contract is [0, 1, 2, 3]`) and went green
again when it was put back.

## How a human runs two clients

```powershell
dotnet build SuperFindGreatDeal.sln

# terminal 1 — leave it running
Godot_v4.7-stable_mono_win64_console.exe --headless --path . -- --server --port 7777

# terminal 2
Godot_v4.7-stable_mono_win64_console.exe --path . -- --windowed --name Talon

# terminal 3
Godot_v4.7-stable_mono_win64_console.exe --path . -- --windowed --name Player2
```

In each client: **Join → Direct Connect → `127.0.0.1:7777`**. Both land in the holding room and
see each other's nameplate. `--windowed` matters when running two — the client is fullscreen by
default. No Steam needed for this path.

Engine flags before the bare `--`, game flags after. A game flag on the wrong side is swallowed and
looks exactly like a hang.
