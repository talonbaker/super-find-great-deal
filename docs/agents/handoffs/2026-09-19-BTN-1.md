## 2. How a press works, end to end

```
client   RoundButton.Press()                       <- InteractHighlighter routed the key here
           -> RoundControls.ClientRequestPress(kind)
           -> RpcId(1, RequestPress, kind)          reliable, channel 21
server   RequestPress
           1. reach, against AUTHORITATIVE positions   -> TooFarAway
           2. RoundButtonRules.Gate(kind, phase, ...)  -> NotNow / NotYourButton
           3. RoundControlFacts.Press(kind, peer, phaseAtPress)
server   HideSeekDriver._PhysicsProcess
           HideSeekLoop.Step(...)                      the round decides
           IRoundFactSource.AfterStep()                -> RoundControls.OnAdjudicate
             RoundButtonRules.ReadResult(before, after, refusal)
server   Rpc(ApplyPressResult, kind, peer, accepted, reason)   reliable + CallLocal, channel 21
every peer  RoundButton.PlayPressResult
             cap down 4 cm + lamp flash            <- EVERY peer
             click / dull thud + 0.15 s shake      <- the presser only
             RoundStripWidget.SayLocal(sentence)   <- the presser only
```

**There is no debounce anywhere in this lane, and that is the packet's instruction taken
literally.** The loop's one-shot fact reading is the idempotence: ten Start presses inside one sim
tick set one bool and produce one transition. A debounce mistaken for a confirmation is the first
of the three playtests the one shipped in-world control failed, and adding one here would be a
second rule about the same thing. What IS deduplicated is the ANSWER — one result message per
(button, peer) per tick — so the cap does not bounce twice for one transition.
`RoundControlFacts.PressesLatched` counts the raw presses, so "the press never arrived" and "the
press arrived and was answered once" stay distinguishable (HONK-1's rule: assert the attempt count
before believing any absence).

### The gate is deliberately narrower than the lamp

`RoundButtonRules.Gate` tests only **phase** and, for Confirm, **role**. Everything the loop
itself refuses on — one player in the room, empty hands, the object still in your hands, nobody
could reach it — is **forwarded**, refused by the round, and comes back with the round's own
sentence. Two authorities on one question is how a button and a loop start disagreeing in a live
session.

So why gate the phase at all? Because `HideSeekLoop` reads `HostPressedStart` only inside its
Holding branch: in any other phase the fact is folded and dropped with **no refusal and no
transition**. The loop is right to be shaped that way — it is phase-dispatched arithmetic — but
that is a silent no-op from the player's side, which is the defect class `INTERACTION-BIBLE.md` §2
exists for. The button is the layer that owes them an answer.

### Why the reach check runs FIRST

Proximity is the anti-cheat gate: a press from a peer whose authoritative body is 28 m away is not
a question the round should be asked at all. It also means a bot in the wrong phase is usually
also in the wrong room and gets `TooFarAway` rather than `NotNow` — see the suite's own note on
what it can and cannot stage.

### The lamp is DERIVED, never pushed

`RoundControls.LampFactsFor(selfPeerId)` gathers phase, roles, human count (`View.Scores.Count`),
and "is the hider holding a rack object" — every one of which already crosses the wire, the last
through `PropManager`'s replicated holder view plus the rack's own children. **So the affordance
costs zero new bytes.** A pushed lamp is a second copy of the round's state that can be stale on
exactly the peer looking at it.

`Lit` means "this will accept a press right now, as far as THIS PEER can see", and the bound is
honest rather than absolute: grab-reachability (REACH-1) is a server-side physics measurement that
never crosses the wire, so **a Lit CONFIRM can still be refused with NOBODY COULD REACH THAT**. The
lamp is the affordance and the sentence is the answer; the bible asks for both (§1 and §2), not for
one that is never wrong.

**The CONFIRM lamp is per-peer** — only the hider ever sees it lit. That is why each capture
session's photographing client is the first to join.

## 3. The target's identity, and what REACH-1 asked for

`RoundControls.TargetPropId` is the one owner. Two readers: `ReachabilityFactSource` (which aims
its physics audit at it) and `DropOffBin` (which tells a delivery from a decoy by it).

- **Set on the hider's PICKUP, not at the Holding → Hiding edge.** REACH-1's handoff asks for
  exactly this, and the reason is layer 3's trigger: its audit fires when the target latches
  Resting, so a target id that only appeared at the transition would miss every settle the hider
  makes while choosing. Following the hands during Holding gives the same value at the edge — they
  are holding it when they press Start — and gives it earlier.
- **−1 on the reset edge**, also REACH-1's ask: a fact about last round's crate is not a fact
  about this round's.
- **Frozen once the round leaves Holding.** The tracking branch only runs in Holding, so nothing
  the hider does in the search room can re-point the target.
- Driven from `RoundControlFacts.Stepped`, which the driver calls every step — so there is one
  clock and no `_PhysicsProcess` ordering between two nodes to get wrong.

**`--reach-target` still works and now WINS for the whole session.** When the flag names a target,
`RoundControls` pins it and the rack never touches it. Without that pin, every suite built on the
flag would break silently: those runs use `--spawn-room search`, nobody is standing at the rack, so
a rack that "tracked the hider's empty hands" would set the target back to none on the first tick
and `Run-ReachTest.ps1`'s phases 2 and 3 would be auditing nothing. Pinning also means the two
owners can never disagree — either the flag owns the target or the rack does.

## 4. The drop-off bin

An open-top box with real static walls and an `Area3D` inside it. **The walls are not decoration:**
a prop thrown at it can miss and roll away, and the seeker can see at a glance whether the thing
went in. A trigger volume with no box would be an invisible rule.

- **The server reads the sensor; clients are told.** One broadcast (`ApplyBinLamp`) carries both
  outcomes. The chime on an accepted delivery plays on **every** peer — it is the one moment the
  hider is entitled to hear, a beat before DOOR-1's door — and the buzz on a wrong prop plays only
  for the **seeker**, because it is an answer to something only they did.
- **Nothing is ejected.** The packet is explicit. A wrong prop buzzes, the lamp flashes red for
  0.5 s, and it stays exactly where it fell. One buzz per prop per second, so a crate bouncing on
  the rim is one answer rather than four.
- **Polled, not signal-driven.** `Area3D.GetOverlappingBodies()` every server physics tick, diffed
  against the last set. A held prop's collider is DISABLED (`Carryable.OnPickedUp`), so the
  interesting case is a shape being re-enabled while already overlapping the sensor — precisely
  where a `body_entered` edge is easiest to lose. The call reads the monitor list the physics
  server already maintains; it is not a shape query.

### "In the bin" is a LEVEL, and it is a DELIVERY

ROUND-1's interface is explicit that `TargetInDropOff` must not pulse — a one-tick edge would lose
the find to a dropped tick. So it latches.

**What it latches on is the target ENTERING while the round is Seeking**, not merely being inside,
and that one word removes a degenerate the packet's wording would have allowed: the hider is alone
in the search room during Hiding and could otherwise hide the object *in the bin*, ending the seek
on its first tick. A bin measures a delivery, not a location. Nothing is ejected to achieve it.

## 5. The rack and the three objects

Three authored `NetworkedProp`s under `ObjectRack` in `HoldingRoom.tscn`. `ObjectRack` is a lookup
and nothing else: it answers "is prop id N one of mine" from its own children, identically on every
peer, which is what lets a CLIENT derive "the hider is holding something off the rack" and light
the START lamp with no new wire field.

`ObjectRack.Resolve()` is **lazy on purpose**. An authored prop's id is assigned by
`PropManager.AdoptAuthoredProps`, which runs on `Gameplay` after the world node is in the tree — so
at this node's `_Ready` every child's `PropId` is still its unassigned default. Resolving there
would cache three wrong numbers, identically on every peer, and the symptom would be a START lamp
that never lights.

### The three placeholder scenes, and what SHELF-1 inherits

`scenes/game/props/DealCan.tscn`, `DealBox.tscn`, `DealProduce.tscn` — **exactly those three
filenames**, because nothing outside them names the objects: the room scene instances them by path,
`PropManager` adopts whatever it finds, and the rack answers from its children. **SHELF-1's landing
is three file overwrites and no code change anywhere.**

What they must keep: **the same colour and the same size class, differing only in shape** (program
§0). That is the whole game. A placeholder set that differed in colour would make the MVP look like
it works and the real set make it stop. Size class is 0.2 m (the orchestrator's ruling), against the
search room's 0.44 m crates — the hidden object is meant to be SMALLER than the clutter, so hiding
it is a real act.

Each wears a gold "great deal" band. Emission is low (0.35) for W7-3's measured reason: a prop at
2.5 blooms past its own silhouette until a cube reads as a ball, and a near-miss whose SHAPE is the
entire mechanic cannot afford that.

**One deliberate deviation inside the placeholders:** `DealCan.tscn`'s mesh is a cylinder and its
**collider is a box** around it. Godot's `CylinderShape3D` is the primitive its 3D solver is least
happy with, and this prop's job is to be set down and stay there — REACH-1's rest audit fires on
every settle and judges the collider. The box is within 1.6 cm of the can's silhouette everywhere.
If SHELF-1 changes it, the thing to watch is `[props] rest not good` in a server log.

## 6. The authored prop ids moved, and they will move again

**This is the one thing in this branch that reaches outside its own lane, so it is stated loudly.**

`PropManager.AdoptAuthoredProps` numbers authored props by sorting on NODE PATH across the whole
world. `HoldingRoom/ObjectRack/Deal_*` sorts before `SearchRoom/Prop_*`, so:

| | before | after |
|---|---|---|
| rack objects | — | **1000, 1001, 1002** |
| `SearchRoom/Prop_0..3` | 1000..1003 | **1003..1006** |

`tests/Run-PlaceTest.ps1` named those four by literal and has been bumped (four constants plus its
doc block). `tests/Run-ReachTest.ps1` uses a *seeded* prop (id 1) and is unaffected in behaviour;
only a comment of its mentions the old numbers.

**SHELF-1's hundred aisle props will do this again**, and any of them sorting before `Prop_0`
within the search room will move that room's own four. The durable fix is for a suite to derive the
ids rather than type them, and this branch adds the line that makes that possible — one per adopted
prop, at world build:

```
[props] authored prop 1002 <- /root/Gameplay/World/Supermarket/HoldingRoom/ObjectRack/Deal_2 (Crate)
```

Done as a constant bump rather than a rewrite in `Run-PlaceTest.ps1` because that is another lane's
suite and four values are the whole dependency. **The next lane to move them should spend the
twenty lines instead.**

## 7. Decisions a reviewer should check rather than take on trust

### No new channel: the press rides `RoundChannel` (21)

DOOR-1 and VOICE-1 are both picking channel numbers in parallel with this branch and cannot see it;
ROUND-1's ladder comment leaves 18/19/20 unclaimed and names 22 as next free. Rather than take one
of those and risk the exact collision `RoundFactSourceTests.TheChannelLadder_HasNoDuplicates` was
written after, these messages ride the round's own channel. They *are* round state — three per
round, reliable, ordered — and ordering them behind the phase broadcast they cause is the behaviour
you want: the cap goes down, then the strip changes. The ladder's argument for separate channels is
about UNRELATED streams head-of-line-blocking each other, and two lanes of one system are not that.
**No protocol bump**, on `SightChannel`'s and `RoundChannel`'s own reasoning: new node, new methods,
no change to the shape of any existing message.

### `PressRefusal` mirrors `HideSeekRefusal`'s ordinals instead of extending it

ROUND-1's enum is untouched and unrenumbered — its handoff says a new value there would be a byte a
stale peer renders as a different sentence than the server refused with. `PressRefusal` 1–4 are
byte-identical to `HideSeekRefusal` 1–4, so `(PressRefusal)(byte)roundRefusal` is the identity map
and `HideSeekText.RefusalSentence` stays the **only** list of those four sentences in the game. The
button's own three sit above them at 5–7, so appending to either enum stays safe. A unit test pins
the correspondence.

### Either player may press START

The fact is called `HostPressedStart` and the loop never asks who pressed it. Both players are
standing in the holding room looking at the same button, and a button that is dead for one of the
two people in front of it is the affordance failure this packet is about. CONFIRM is the hider's
(checked, even though in a real session nobody else can reach that room — "unreachable in practice"
and "refused" are different guarantees and only the second survives a level edit); END is either
player's, per `AnyPressedEnd`.

### `RoundStripWidget.SayLocal` rather than a second plate

Three of the seven refusal reasons never cross the wire (they are the button's own), so the presser
needs a local channel for them. It reuses the strip's existing two-second latch and flash, so a
local sentence and a wire sentence are indistinguishable to read — which they should be, because to
the player they are the same event. A second plate for three of seven reasons would teach them two
places to look under time pressure.

### One `Sfx` ordinal taken: `Buzzer = 43`

`Sfx.Buzz` is an INSECT fly-past whose own implementation comment says it deliberately avoids
sounding like a machine; using it for the bin's rejection would be a bee where an answer belongs.
`Sfx.Thunk` is already spoken for as the dull thud of a refused *button press*, and one sound for
two different refusals teaches a player that the game makes a noise rather than what it means. So
one new recipe: a short falling two-tone rasp, 0.26 s, synthesised like every other member.
**24–42 are left unused** for DOOR-1, SFX-1 and CLOCK-1, with a comment saying so, because four
lanes are appending to this pinned enum off one base and a textual merge that renumbered one would
silently re-point every presentation `.tres` that names it. Everything else reuses existing
recipes: `Pop` for an accepted click, `Thunk` for a refused thud, `Chirp` for the bin's chime.

### The buttons are authored INLINE in each room, not instanced from a prefab

A `RoundButton.tscn` instanced three times is the obvious move and is the wrong one here:
`SupermarketWorldSelfTest` compares each room's PACKED node count against its LIVE one, and an
instanced sub-scene contributes **one** node to the packed side and **all of its children** to the
live side. (The existing `Carryable` stop in `CountNodes` is exactly that exception, carved for
props.) Authoring the plate in each room keeps that check honest and keeps the rule the check exists
for — every part of a level is authored in its own scene file, openable in the editor. The cost is
one duplicated sub-resource block per room; the benefit is that the compliance test covers all of
it. **This also answers CLOCK-1's note about prefabs needing to be added to a coverage list: there
are no prefabs in this lane to add, and the three `Deal*.tscn` prop scenes ride the existing
`Carryable` exception exactly as `Crate.tscn` already does.**

### The kind comes from a GROUP, never an `[Export]`

Nested-scene exported script properties read back as their C# defaults on this Godot/Mono build —
measured three times in this repo now (`PropManager.AuthoredKindOf`'s note, CARRY-1's `Interactable`
note, CLOCK-1's third). Nothing in this lane reads an authored export: the kind is a group, the
press radius is a `const`, and the face label is authored *and* checked against the tested copy
table at `_Ready` with a loud warning on a mismatch.

### The cap travels along the button's local −Z

Every button is authored with **+Z pointing out of the surface it is mounted on**, so one rule
covers a button on the −Z wall, the −X wall and the +X wall with no per-instance special case — and
a cap that pressed along world −Y would slide DOWN the wall instead of going into it. A `.tscn`'s
twelve `Transform3D` floats are basis ROWS, so the same rotation written column-wise is its inverse
and would point the plate into the wall. **The server prints each button's measured facing at world
build** and the suite asserts all three, so this is checkable from a log rather than only from a
render.

### One staging defect the suite found in itself first

The suite's FIRST run failed phase 3 with nothing in the bin, and its own failure message said
what to do: read the server log before concluding anything about the bin's rule. The log said
`place denied peer=N reason=TooFarToPlace`, twice. Two constants had composed —

unconditionally so the next reader does not have to go looking.
