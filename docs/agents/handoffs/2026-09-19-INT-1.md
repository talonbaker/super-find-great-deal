## 7. Ruling 6 — `--spawn-index`, and a race ended

SHELF-1 §6.3 measured spawn markers being dealt by join order and join order racing: *"the box bot
drew marker 2 once and marker 1 the next time, and the run where it drew the far marker went red on
a pickup that never happened."*

- `scripts/game/world/SpawnPin.cs` — engine-free: parse `"BotA=2,BotB=0"`, answer an index by name.
- `tests/unit/SpawnPinTests.cs` — 20 tests.
- `--spawn-index <spec>` — a **SERVER** flag, empty by default.
- `Gameplay.ApplySpawnPins()` — four lines: read the name, `RoundTeleport.ServerMove` to the marker.

**Nothing goes onto any wire, and that was the design constraint.** The obvious implementation is a
handshake field, and the handshake payload is versioned — widening it would owe a second
`ProtocolVersion` bump this wave has already spent. So the pin matches on `SandboxAvatar.DisplayName`,
which **already replicates**. The cost is that the server does not know who a peer is at
`OnPeerConnected`, so this is a poll acting once per peer as soon as the name arrives.

**A client cannot reach it.** Only the process that started the server can pin. Deliberate: a
self-teleport verb is an anti-cheat surface and a merge lane is not the place to open one.

**Proved to DECIDE something, not merely to run.** The four pins applying is not proof — the bots
might have landed there anyway. So the spec was **reversed** in a one-off probe with the bots
launched in the same order:

```
[server] spawn pins PlaceBotA=3,PlaceBotB=2,PlaceBotC=1,PlaceBotD=0
[server] spawn pinned name=PlaceBotA marker=3 at=(41.50,1.10,-2.10) moved=True
[server] spawn pinned name=PlaceBotD marker=0 at=(35.50,1.10, 0.00) moved=True
```

**The first joiner landed on marker 3 and the last on marker 0.** The position follows the NAME.

Wired into the three suites that stage fixtures in the dressed search room, each using that suite's
own stated table. **It did not fix `Run-MaterialSfxTest`** — see §4.3, which is how SHELF-1's stated
cause came to be ruled out.
