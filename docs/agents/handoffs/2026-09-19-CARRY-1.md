## 1. The carry, and why the spring lives where it does

The packet offered two ways to give a networked holder the feel system's carry: bind the lab's
`Interactor` to the networked prop's body, or port `Interactor`'s carry update into
`NetworkedProp` — *"pick the one that leaves `feel/` intact and say why"*. **Neither, as written,
does**, so the answer is a third thing and this is the reasoning.

- **Binding `Interactor`** drags in a second targeting authority. It owns a proximity `Area3D`, an
  aim cone with its own half-angle and hysteresis, and a line-of-sight rule — all deciding "what
  would E act on" next door to `InteractTargeting.Pick`, which is this repo's *one* rule for that
  question and the thing a playtest bug was fixed by centralising. It also wants a `Camera3D`,
  which is the exact dependency CARRY-1 was told not to take while FP-1 replaces the camera.
- **Copying the update into `NetworkedProp`** leaves `feel/` untouched and leaves the spring with
  **two homes**. That is how a feel system and its copy drift apart one tuning session at a time,
  and the copy is always the one nobody re-tunes.

**So the maths moved into `scripts/game/sandbox/feel/CarrySpring.cs` and both callers read it.**
`Interactor` keeps every dial, every decision, and all of its targeting and release logic; what it
lost is the arithmetic, which it now calls instead of inlining. `NetworkedProp` constructs one for
the local holder. `feel/`'s own gate (`Run-FeelTest`) is the proof the extraction changed nothing.

### Who runs the spring

`ApplyPropState`'s Held case now passes `springOnThisPeer: holderPeerId == Multiplayer.GetUniqueId()`.

- **The holder's peer** (host included — a host is a player) carries the prop on the spring:
  `NetworkedProp.BindToHolderSpring` → `Carryable.OnPickedUpBySpring` → `NetworkedProp.StepSpring`
  every physics tick.
- **Every other peer** is byte-for-byte unchanged: `CarryController` + `Carryable`'s anchor chase.

Running the spring on every peer would mean each integrating a slightly different spring against a
slightly different *interpolated* anchor, so no two players would agree where the crate is — for a
purely cosmetic gain. Running it on the holder alone costs one view-to-view mismatch (measured
below) and buys the thing the carry was rebuilt for: on the screen of the person holding it, the
object has weight.

**`Carryable.OnPickedUpBySpring` deliberately does NOT snap the prop to the hand.** `OnPickedUp`
does, because its chase would otherwise slide the prop visibly up off the floor; a spring seeded at
the item and allowed to travel is the better answer to the same problem, and it is the documented
anti-pop (`CarrySpring.Seed`). Freeze, collision-off, the pickup pop and the pickup cue are
identical.

**`Carryable.IsHeld` grew a second arm** (`_holder != null || _springHeld`). A spring-carried prop
has no `CarryController` at all, so the old test read FALSE for the thing in the local player's
hands — which would have shown the hover outline on a held prop, offered it back as a free grab,
and disarmed the guard that stops E from discarding what you are carrying when somebody else wins
a race.

### Rotate held

`HeldPropRotator` (a node built only for the local human player, beside their camera) reads
`rotate_held` — right mouse button — and writes `SandboxAvatar.HeldPropLocalRotation`, a `Basis`
local to the holder. `NetworkedProp.StepSpring` folds it into the pose the spring trails.

- Mouse X → yaw, mouse Y → pitch, both composed on the left so every step stays in the holder's
  frame. Wheel → 15° yaw notches, because 15 divides 90 and 360 exactly and the analogue mouse is
  bad at square.
- **It consumes the mouse while active** (`_Input` + `SetInputAsHandled()`), so the camera does not
  turn at the same time. `SandboxCamera` reads the mouse in `_UnhandledInput`, which runs after.
  **FP-1 / INT-1: this holds for any camera that reads the mouse as *unhandled* input.** It is the
  Godot idiom and the current camera's habit, but it is a coupling worth knowing about.
- `rotate_held` shares its physical button with `aim`. That is not a clash in this game: `aim`
  drives the raise-to-aim body rig, which is cosmetic, on the body first person hides, for a verb
  that does not exist yet. Split them the day one does.
- **No new `MoveIntent` field**, per the packet. The rotation lives on the holder's machine and
  becomes everyone's business exactly once — in the transform a PLACE sends. Drop and throw do not
  carry it, which is the honest difference between setting a thing down and getting rid of it.

## 2. The place RPC contract

```csharp
// Client -> server. The transform IS the message: rotate-held is unreplicated, so the
// orientation the player lined up exists only on their machine until this call carries it.
public void ClientRequestPlace(int propId, Transform3D intended);

[Rpc(MultiplayerApi.RpcMode.AnyPeer, TransferMode = MultiplayerPeer.TransferModeEnum.Reliable)]
private void RequestPlace(int propId, Transform3D intended);
```

Server validation, **in this order**, each arm refusing with its own reason:

| # | Test | Refusal |
|---|---|---|
| 0 | sender is a known peer, not control-denied | *silent* (no trustworthy peer to answer; a reply here is a reflection surface — same rule grab follows) |
| 1 | the transform is finite | `TooFarToPlace` |
| 2 | the sender holds **this** prop | `NotHolding` |
| 3 | prop/avatar/registry resolve and the prop is Held | `Gone` |
| 4 | holder's body within `GrabRange` of the prop (the same slack rule grab uses) | `OutOfRange` |
| 5 | `intended.Origin` within `PlaceReachM + GrabRangeTolerance` of the holder's **hand** | `TooFarToPlace` |
| 6 | `PlacementIntegrity.Check` — bounds, then overlap | `OutsideRoom` / `DoesNotFitThere` |
| 7 | `PlacementValidator?.Validate` (default: none registered) | the validator's own ordinal, or `NotAllowedHere` |
| 7b | if the validator MOVED the placement, integrity runs **again** on the moved transform | `OutsideRoom` / `DoesNotFitThere` |

Pass → `node.NoteLastGood(at)`, `_registry.Release(propId, at)`,
`Rpc(ApplyPropState, Loose, holder 0, at)`, `node.PlaceLooseServer(at)`.

`PlaceLooseServer` puts the body exactly at `at` and hands it to physics with **zero linear and
zero angular velocity** (`Carryable.OnPlaced`). Loose rather than straight to Resting on purpose: a
placed prop still has to fall the last millimetre onto whatever is under it and still latches
through the server's own settle loop, so a placement balanced on a rolling ball behaves like
physics rather than like a decision. What place removes is the DROP's toss arc and `OnThrown`'s
*random* tumble spin — both of which exist to make a discarded object look discarded, and both of
which would spin away the orientation the player just lined up.

Fail → `DenyPlace(peer, reason)`, reliable, to the one peer that asked, logged server-side; **the
prop stays in the hand.**

### The refusal, on the presser

`SandboxAvatar.OnPlaceDenied` → bump squish + the profile's `ActorEvent.Bump` bonk + **the reason
in words** via `Ui.RefusalNotice.Say(...)`, a transient plate reusing `ConsequenceWarning`'s
non-occludable lower band.

**The grab path got the words too**, and that is a small deliberate addition. `OnGrabDenied`'s own
comment has always conceded that the cue *"deliberately does not say WHY"*; that was defensible
with five reasons and is not with twelve, and `INTERACTION-BIBLE` §3/§7's scar tissue is
specifically a warning that did not say which key. `CarryRefusalText` holds both maps, engine-free,
and `tests/unit/CarryRefusalTests.cs` asserts **every ordinal but `None` has its own non-generic
sentence** — so adding a refusal reason and forgetting to say it out loud turns xUnit red.

## 3. `PlacementIntegrity.Check` — the signature, and what it does

```csharp
public static Verdict Check(RigidBody3D propBody, Transform3D at, Rid? excludeHolder = null,
    float overlapToleranceM = DefaultOverlapToleranceM);

public enum PlacementFault { None = 0, OutsideRoomBounds = 1, Overlapping = 2, NoShape = 3 }

public readonly record struct Verdict(PlacementFault Fault, float PenetrationM, string Detail)
{
    public static readonly Verdict Ok;
    public bool Allowed => Fault == PlacementFault.None;
}
```

The packet's engine-facing signature is the two-argument one and it still is:
`excludeHolder` defaults to null precisely because **REACH-1's rest-time audit has no holder**.
Placing a crate at arm's length in front of you overlaps your own capsule, so the place path passes
the holder's `Rid`; a settle audit does not.

**Test 1 — bounds.** Every corner of the shape's local extent, at the candidate transform, inside
ONE room's `RoomBounds` box, plus `BoundsEpsilonM` (0.02 m — a crate set down *on* the floor has
its bottom face exactly at the volume's floor, and an exact float comparison would refuse it about
half the time). One room, not the union: the rooms are 40 m apart behind solid walls, so a
placement straddling two is a symptom, not pedantry. **No bounds volume anywhere is a PASS**, which
is what keeps the CI worlds (`open`, `propsync`, where every other carry suite runs) working.

**Test 2 — overlap.** `PhysicsDirectSpaceState3D.CollideShape` at the candidate transform, mask 1
(static geometry *and* released props — a held prop is on layer 0 and is correctly invisible),
excluding the prop itself and the holder, margin 0. The returned contact **pairs** give penetration
depth directly; `IntersectShape` alone could not tell a crate resting on a shelf from a crate
inside it, which is the whole distinction the tolerance exists for. On the refusal path only, a
second one-result query names the blocker for the log.

**`HalfExtentsOf`** is an explicit switch over Box/Sphere/Capsule/Cylinder rather than
`Shape3D.GetDebugMesh().GetAabb()`, which allocates an `ArrayMesh` per call on a path that runs
once per placement **and once per settle for every prop in the room**. An unknown shape falls back
to a conservative 0.25 m cube, which errs toward refusing rather than toward waving a prop into a
wall.

### `LastGoodTransform` — recorded, not used

`NetworkedProp.LastGoodTransform` starts at the spawn/adoption transform and is written in exactly
two places:

1. the place RPC, on the transform that passed;
2. **every Resting latch**, but only if `PlacementIntegrity.Check` passes at the rest transform.

That second one is the `§5b` sentence "`LastGoodTransform` is also set on every Resting latch only
if the same two tests pass" and it costs one shape query per settle event, which is what §5b priced
it at. A rest that FAILS is left exactly where physics put it, logged (`[props] rest not good …`),
and the previous good transform is kept. **CARRY-1 deliberately ships no correction** —
depenetration and the last-good fallback are REACH-1's layer 2, and shipping half of it would be a
prop teleporting with no audit behind it.

### `IPlacementValidator` — the hook, with the excerpt

```csharp
public interface IPlacementValidator
{
    PlacementDecision Validate(NetworkedProp prop, Transform3D intended, int holderPeerId);
}

public readonly record struct PlacementDecision(
    bool Allowed, Transform3D Transform, PropManager.PlaceDenial Reason)
{
    public static PlacementDecision Allow(Transform3D at);   // yes, exactly there
    public static PlacementDecision Snap(Transform3D to);    // yes, but THERE
    public static PlacementDecision Refuse(PropManager.PlaceDenial reason);
}
```

`PropManager.PlacementValidator` is null by default, and null means free placement — the R.E.P.O.
verb the game is built on. It returns a **transform** because a snap pad's whole job is "yes, but
there" (`InteractionSlot.RestPose` is exactly that shape), and a moved placement is re-checked
because a pad that snapped a crate into a wall would be the §5b defect arriving through the one
door that skipped the check.

## 4. Throw: the aim ray, and the mismatch the packet asked me to document

`RequestThrow` now releases along the **replicated aim ray**
(`AimQuery.DirectionFromYawPitch(avatar.AimYaw, avatar.AimPitch)`), pitch included, instead of
`-avatar.GlobalBasis.Z` flattened. Drop and scatter keep the body facing on purpose: both mean
"this ends up around me", and aiming at the ceiling should not lob a discarded object over your
shoulder.

**Why it had to change.** `MoveState.Yaw` tracks where the body is *travelling*, not where the
player is looking. Nobody could see the difference in third person while walking forward. It
becomes absurd the moment FP-1 lands: a player standing still, looking up at a shelf, would throw
the crate at their own feet.

**The mismatch, stated rather than hidden.** The holder's own screen shows the prop leave the hand
carrying the **spring's** velocity — throw while sprinting and it departs faster, because that is
what `Interactor.ThrowScale` does. The server, which has no spring for a remote holder and must
compute the same answer for every peer, uses the ray and a **fixed** speed
(`ThrowForwardSpeed` 7.5 / `ThrowUpSpeed` 3.2, × `CarryThrowScale`). So the first frames of a throw
are the holder's local flourish and everything after is the server's arc, differing by the holder's
own motion at release. The alternative — replicating the spring's velocity — would make the length
of a throw a number the client reports about itself, which is the one shape
`RISK-AUDIT-2026-07-12.md` §4.1 says never to trust.

**Consequence for scripted bots, and it is not cosmetic.** A bot leaving `AimYaw` at its default
would throw at a fixed world bearing regardless of where it walked, and `Run-ThrowTest`'s
out-of-bounds recovery case would silently stop being staged — the invisible kind of green. So
`ScriptedCarryIntentSource` now reports the heading it is steering on
(`Mathf.Atan2(-dir.X, -dir.Z)`, `AvatarMotor.ResolveYaw`'s convention) as `AimYaw`, with
`AimPitch` left at 0. That makes the bot's aim agree with the bot's body instead of inventing a
second answer, and every existing suite's geometry is preserved by construction rather than by a
tolerance.

## 5. Bindings and knobs

| Verb | Binding | Notes |
|---|---|---|
| Pick up / put down | `interact` (E) | one key, one grammar |
| Turn what you're holding | `rotate_held` (RMB) + mouse / wheel | **new action** in `project.godot` |
| Throw | `throw` (Q) | unchanged binding, new direction rule |

All three are in `ControlGlyphs.Sections` under CARRY, so the How-to-Play panel resolves them live
from the input map rather than printing a hardcoded letter. The row was **renamed** "Pick up /
drop" → "Pick up / put down" because the second half now means two things.

**E, while holding, resolves by where you are looking:**

- aiming at something solid within `SandboxAvatar.PlaceAimProbeM` (3.0 m) → **place** at the
  spring's current transform;
- otherwise → **drop** (the existing light toss).

The ray is built from `MoveIntent.AimYaw/AimPitch`, **never from a camera node**, so it stays
correct under either camera while FP-1 is in flight. The held prop cannot occlude its own placement
(layer 0 while held); the avatar's own body is excluded explicitly, because at a steep downward
pitch the first thing the ray meets is its own shoulder.

| Knob | Default | What it governs |
|---|---|---|
| `PropManager.PlaceReachM` | **0.9 m** | how far the OBJECT may end up from the hand. Small on purpose: the verb is "put it where I am holding it", and a generous value is telekinesis — and, worse, a way for a hider to post the target through a shelf they cannot reach. |
| `PropManager.PlaceOverlapToleranceM` | **0.02 m** | penetration allowed before `DoesNotFitThere` |
| `PlacementIntegrity.BoundsEpsilonM` | 0.02 m | slack on the bounds test |
| `SandboxAvatar.PlaceAimProbeM` | 3.0 m | how far ahead E looks for a surface to place ON |
| `HeldPropRotator.MouseRadiansPerPixel` | 0.010 | rotate-held mouse sensitivity (independent of the camera's) |
| `HeldPropRotator.WheelStepDegrees` | 15° | one wheel notch |
| `CarrySpring` dials | `Interactor`'s shipped defaults | `MassReference` 10 kg, `LightResponse` 20, `HeavyResponse` 6.5, `RotationResponse` 0.7, `SwingDegrees` 16, `SwingReferenceSpeed` 3.2, `SwingSmoothing` 0.12 |
| `NetworkedProp.CarryDroopM` | 0.11 m | sag at full heft (a HAND fact, so it lives with the anchor, not the spring) |
| `Ui.RefusalNotice.HoldSec` | 2.2 s | how long a refusal stays on screen |

## 6. Level content, and what it is for

Three `RoomBounds` `Area3D`s, one per room section scene, group `room_bounds`, sized to the
**interior** (floor top to ceiling underside, wall inner face to wall inner face). The vestibule has
none deliberately: nothing is placed there and DOOR-1 owns it.

`SearchRoom.tscn` also gained, as a **fixture** rather than as dressing:

- **`SearchPillar`** — a 1 × 2 × 1 m freestanding static block at local (6, 1, 2.5). It exists
  because "inside a wall" needs a transform that is inside the room's bounds *and* inside static
  geometry at once; every real wall **is** the boundary, so a crate pushed into one fails the
  bounds test first and the overlap test could never be proved to fire at all. SHELF-1 may delete
  it the moment a real shelf back does the same job — leave a replacement that is static, interior,
  and at least as deep as a crate.
- **`Prop_0..Prop_3`** — four authored props, adopted as ids **1000–1003**.
- **`SearchSpawn_2` / `SearchSpawn_3`** — two more markers, so a four-bot suite gets four distinct
  standing spots. `SupermarketWorld.Contract`'s search row went 2 → 4.

### How SHELF-1 / TASK-1 / BTN-1 add props and pads

**A prop** is a `Node3D` with the `NetworkedProp` script and a child literally named `Body`
instancing `Crate.tscn` (or `Sphere.tscn`):

```
[node name="Prop_0" type="Node3D" parent="."]
transform = Transform3D(1, 0, 0, 0, 1, 0, 0, 0, 1, -4, 0.22, 0)
script = ExtResource("2_netprop")

[node name="Body" parent="Prop_0" instance=ExtResource("1_crate")]
```

- `NetworkedProp._Ready` **binds** that child rather than building one. The name `Body` is not
  cosmetic.
- `PropManager.AdoptAuthoredProps` assigns ids by sorting on **node path**, identically on every
  peer, starting at 1000. **The numbering in the scene IS the id order** — renaming one renumbers
  the rest, so anything that names an id (a suite, a drop-off bin, the target prop) is coupled to
  the names.
- `Crate.tscn` and `Sphere.tscn` now carry an **`Interactable`** child as well as their
  `Carryable` script, so every prop satisfies the packet's "RigidBody3D with `Interactable` **and**
  `NetworkedProp`". It is load-bearing, not decoration: `HeftKg` is the single number the spring
  turns into lag, droop, swing and squash, and `HoldOffset` / `HoldRotationDegrees` are where and
  how the thing rides. A prop that wants to read heavy sets its body's `Mass`, not a second dial.
- **Nested-scene `[Export]`s still read back as defaults on this Mono build** (`AuthoredKindOf`'s
  note). Do not gate behaviour on one. `Interactable`'s exports are subject to the same trap —
  `HeftScale`, `Tag`, `HoldOffset` authored on an instanced prefab will read as their C# defaults.
  Set `mass` (a native property, which survives) and live with the rest, or set them in code.
- y = half-height (0.22 for a crate): props start resting on the floor.

**A pad** (TASK-1) registers an `IPlacementValidator` on the server's `PropManager` — see §3.
`InteractionSlot` is *not* wired in: it is a client-side lab type and the server knows nothing
about it. The honest shape is a validator that reads the pads the server already knows about and
returns `PlacementDecision.Snap(pad.RestPose(intended))`.

**A drop-off bin** (BTN-1) has two options and they are different verbs: refuse the wrong prop at
place time with a validator (the player is told, in words, before it lands), or accept everything
and buzz on the wrong id (the player finds out after). §5's staging wants the second; the first is
available for free if a playtest says the buzz is confusing.

### `--spawn-room` (new, server-side)

Empty by default, so an ordinary session is unchanged. Set to `holding` / `search` / `task`, the
server spawns everyone at that room's markers. It exists because the three rooms are sealed boxes
40 m apart: a suite that needs a bot in front of the search room's props has no other way to get
one there, and seeding fixture props into the holding room instead would test the verb against
content no lane owns. Read in exactly one place (`Gameplay.SpawnPositionFor`), and it never moves
anybody after they spawn — **ROUND-1 still owns the real thing** (`RoomTeleport` on a phase change).

### One self-test rule changed, deliberately

`SupermarketWorldSelfTest.CountNodes` now **stops at a `Carryable`**: a prop's body counts as one
node and its insides are not walked. The rule the check enforces is "every part of a LEVEL is
authored in its scene file"; a prop is an instanced prefab whose own script has always built its
cosmetic children at runtime (the inverted-hull outline, the blob shadow), none of which appears in
the packed state of the room that instances it. Counting into a prop compares the room's authored
nodes against the room's nodes *plus a prop's private furniture*. **What it does not weaken:** the
prop node and its body still count, so a room that SPAWNS a prop in `_Ready` still turns this red,
and all scenery is still walked to the leaf.

### The place suite, and it was proved able to fail

`tests/Run-PlaceTest.ps1`: one server in the real `supermarket` world with `--spawn-room search`,
four bots, each grabbing its own prop so nothing contends.

| Bot | Does | Asserted |
|---|---|---|
| A | grabs 1000, carries it to (40, ·, 0), places at (40.2, 0.225, 0) yaw 35° | **B** sees it unheld, within 0.05 m and 5° |
| B | grabs 1003, stands still, places 5 m away | refused `TooFarToPlace` (3), still holding 1003 |

look like "still held", and telling them apart is the whole argument for the enum existing.

Orientation is checked because position alone cannot see a crate that landed square but face-down;
`BotHarness.PropSample` now logs each prop's world quaternion.

**The fault plant.** `PlacementIntegrity.Check` was made to `return Verdict.Ok` unconditionally and
the suite re-run. It went red on exactly the right four lines — C and D both lost their props into
the pillar and through the wall, and both reported refusal ordinal 0:

```

  - bot C: newest place refusal was ordinal 0, expected 4 - inside the pillar (DoesNotFitThere)
  - bot C: prop 1001 holder=0 in the final sample, expected 429151813 - a REFUSED place must never
    cost the player what they were carrying
  - bot D: newest place refusal was ordinal 0, expected 5 - outside the room bounds (OutsideRoom)
  - bot D: prop 1002 holder=0 in the final sample, expected 1875057456 - ...
```

## 8. Deviations from the packet

1. **The spring lives in a third file, not in `Interactor` and not in `NetworkedProp`.** Reasoned in
   full in §1; the packet explicitly asked for the choice and the reason.
2. **`PlaceDenial` is its own enum rather than more `GrabDenial` ordinals.** The packet said "a
   `GrabDenial`-style enum", which I read as the shape (reliable, addressed, append-only, never
   silent) rather than the identity. The two verbs refuse for disjoint reasons and merging them
   would make every consumer of a grab refusal switch over reasons a grab can never produce.
3. **Two bounds/overlap reasons rather than one `DoesNotFitThere`.** §5b names the reason for the
   overlap case and leaves the bounds case unnamed; the packet's smoke asks for "a place outside
   `RoomBounds` is refused" without naming it. `OutsideRoom` says a different, more useful thing.
4. **The refused-grab path also gained reason text.** Not asked for. It is three lines, it removes a
   defect the code's own comment admitted to, and it is the same channel the place refusal needed
   anyway.
5. **`--spawn-room` and two extra search-room spawn markers.** Not asked for; §6 explains why the

## 9. Measured

### Spring-vs-anchor mismatch

**The packet's number: mean 0.372 m, peak 0.403 m, at a sustained walking speed.**

Measured off `tests/logs/carrydrift.jsonl` — `Run-CarryDriftTest`'s bot grabs a crate and patrols a
21 m lane at ~3.6 m/s for the whole run, never standing still, which is exactly the condition the
question is about. Samples from 3 s in (after the grab and the first leg settle), n = 83:

| Quantity | mean | median | peak | min |
|---|---|---|---|---|
| `off` — prop to the holder's bare carry anchor | **0.372 m** | 0.383 m | **0.403 m** | 0.226 m |
| `springLag` — prop to the spring's own hand anchor (load lift + droop folded in) | 0.344 m | 0.358 m | 0.361 m | 0.164 m |
| `bd` — prop to the holder's rendered body | 0.997 m | 0.998 m | 1.047 m | 0.946 m |

**That is the whole of the mismatch.** The holder sees the prop at the spring's position; every
other peer derives it from the holder's carry anchor, which is where `off` measures from. So at a
sustained walk the two views of one crate differ by about **37 cm**, and at a standstill the spring
catches up and the difference decays to zero — a critically damped spring has no steady-state error
against a stationary target (`CarrySpringTests.Converges_OnAStationaryHand` pins it at < 5 mm).

It matches the closed form: steady-state lag for a critically damped spring under constant velocity
is `2v/ω`, and a 1 kg crate is heft 0.1, so `ω = lerp(20, 6.5, 0.1) = 18.65` and
`2 × 3.6 / 18.65 = 0.386 m`. Measured 0.372. The dial that moves it is `HeavyResponse` /
`LightResponse`; a heavier prop lags further by construction, which is the point.

**A near miss worth recording, because it was luck rather than design.** `Run-CarryDriftTest`'s caps
are on `bd`, the prop's distance from the rendered BODY, with `MeanMax` 1.15 m and `PeakMax` 1.45 m
against BASE-1's measured 1.010 / 1.063. A 0.37 m lag looked certain to blow through them. It did
not, because the lag points *backwards along travel* and the carry anchor is *in front of the body*,
so the lag moves the prop toward the body rather than away from it: `bd` went **down**, 1.010 →
0.997. The caps were never touched and nothing was loosened to accommodate this packet. But the
sign of that cancellation is a fact about where the anchor sits, not a guarantee — a future anchor
behind or beside the body would put the whole lag straight into `bd`. Whoever moves the carry
anchor should re-read this paragraph.

**During a place** (`Run-PlaceTest`, bots that stand still far more than they walk): mean 0.047 m,
peak 0.743 m over 275 held samples. The peak is the first ticks after a grab, when the spring is
still travelling from the item to the hand — the anti-pop, doing its job.

### And one red that was NOT a flake — the regression this marathon caught

The FIRST marathon on this branch went **30 PASS / 2 FAIL**, and one of the two was mine.
`Carry: server-authoritative` printed:

```
bot A: observed A grab prop 1 at 1.00s but never observed the drop before the log ended
```

which looks exactly like the staging flake the rules file documents for this suite, and was not.
The server log named it in one line:

```
[server] place refused peer=979401151 prop=1 Overlapping (penetration 0.294 m)
         penetrates /root/Gameplay/Players/545392650 by 0.294 m (tolerance 0.020 m)
[server] place denied peer=979401151 reason=DoesNotFitThere
```

**Two bots stood at the same crate.** The holder's eye-height aim ray met the other bot's capsule,
so E resolved to PLACE rather than DROP; the placement was then refused because the crate — held
out in front of the holder's chest — penetrated that capsule by 0.294 m. The prop stayed in the
hand and the drop the suite was waiting for never happened. **Pressing "put this down" next to a
friend did nothing at all**, in a two-player co-op game where standing next to your friend is most
of the game.

Two fixes, both of which are what §5b already said:

1. `PlacementIntegrity`'s overlap query excludes **every live avatar**, not just the holder. §5b's
   wording is "static geometry and every other prop" — a player is neither. A wall traps a prop
   forever; a person walks away a second later and the settle resolves the contact by itself.
2. The place-aim probe excludes every live avatar too. A person is not a surface you set things on.

After the fix, zero `place refused` lines in that suite's server log, and
`Run-CarryTest.ps1 -SkipBuild` standalone went **2/3 PASS** — the one red being the byte-identical
documented staging string (`C's grab never converged, so the disconnect-release was never staged`),
which is exactly the rate BASE-1 measured for this suite on an unmodified tree.

**The lesson is the one the rules file keeps repeating and I nearly got wrong anyway: read the
FAILING CHECK and then read the server log, before reaching for the load-flaky list.** This red was
in the list's own vocabulary and was a real defect. A flake list is a hypothesis, not a verdict.
