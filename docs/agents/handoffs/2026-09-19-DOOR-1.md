## 1. The door is round state, and that is the whole architecture

`BurstDoor` subscribes to `HideSeekDriver`'s three events on **every** peer. When the round enters
`Together` carrying the server's Found tick T, each peer plays its own copy of `StartleTimeline`
from the one reliable, ordered message that carried T. Nothing about "open" is ever requested by a
client, and nothing about it is sent by the door.

**Why not the obvious design.** The program names
`Watis_Game@origin/main:scripts/game/world/puffinlab/TinyDoor.cs` as the thing to read and the
thing not to repeat. Its leaf-and-blocker construction is right and is reproduced here; its
`Open()` is local-only, and its own comment concedes that making it authoritative "means a new
networked interactable". A second networked interactable would be a second source of truth about
the one instant the whole round hangs on, and a peer that missed the packet would be a player
standing in front of a door that, for them, never opened.

**T is an identity, not a clock.** `HideSeekState.Tick` is the loop's own counter and a client
never runs the loop, so no client can convert T into its own time base. What every peer *does*
share is the message. Each starts its own timeline when that message lands, and `_stagedFoundTick`
de-duplicates on T so the wire restating `FoundTick` in every `Together` message cannot re-burst
anything.

**The late joiner.** `HideSeekDriver.Found` deliberately never fires for a peer that did not
witness the transition (ROUND-1's rule: bursting for a client that arrived after the find would
announce a find it missed). `BurstDoor.CatchUpIfAlreadyOpen` polls `View` instead: phase
`Together` or `Tally` with a real `FoundTick` means **the door is simply open** — leaf at
`LeafOpenDeg`, blocker off, no bang, no kick, no tell, because none of those happened to them.

## 2. The knob table

`scripts/game/round/StartleTuning.cs`. Every row is named by the packet or by program §5 and
nothing else is.

| Knob | Default | What it governs |
|---|---|---|
| `TellSec` | **0.4 s** | how long the tell runs before the burst. **0 = no tell at all** (§5), which is a missing beat and not a zero-length one — see `StartleTimeline.Beats` |
| `TellLightDipFraction` | **0.40** | how far the task-room lamp drops during the tell, as a fraction of its authored energy |
| `LeafOpenSec` | **0.12 s** | shut → `LeafOvershootDeg` |
| `LeafOpenDeg` | **110°** | where the leaf rests |
| `LeafOvershootDeg` | **125°** | the bounce. Validated to be ≥ `LeafOpenDeg` |
| `LeafSettleSec` | **0.25 s** | overshoot → rest |
| `LeafCloseSec` | **0.6 s** | the reset's close |
| `BurstRadiusM` | **3.0 m** | how far the shove reaches |
| `BurstImpulseNs` | **6 N·s** | the shove at the doorway, falling off linearly to zero at the radius |
| `ForceDropOnBurst` | **on** | the flinch: the server opens the hider's hand at the burst |
| `KickDegrees` | **4°** | the hiders' camera kick |
| `KickSec` | **0.3 s** | how long it takes to decay to nothing |
| `BangFlatDb` | **−3 dB** | the second, flat bang on the hiders' intercom |
| `FakeKnockRatePerMin` | **0 (off)** | §5's first anticipation knob |
| `SeekerKnockKey` | **false (off)** | §5's second |
| `SeekerHeatOnIntercom` | **false (off)** | §5's third |

### The JSON overlay — `--startle-file <path>`

`MotorTuningFile`'s document, verbatim in shape: a `version`, a `savedUtc` and a **sparse**
`values` object carrying only what differs from the shipped defaults.

```json
{ "version": 1, "values": { "TellSec": 1.2, "BurstImpulseNs": 9 } }
```

Every malformed case is handled and reported as a `[startle]` warning: bad JSON or a wrong
version discards the **whole** document (half a corrupt file is a tuning nobody authored), an
unknown knob is ignored, a non-number takes its shipped default, and everything surviving goes
through `StartleTuning.Validate` (finite, in range, and `LeafOvershootDeg ≥ LeafOpenDeg`). Names
match case-insensitively and a bool takes `0`/`1` or `true`/`false`, because the file is
hand-edited and refusing `"ForceDropOnBurst": false` on a technicality would be a trap.

**Three deliberate differences from `MotorTuningFile`, all about who writes it.** That file is
written *by* the game and read back, so a fixed private `user://` location is right for it; this
one is written by a person in a text editor and only ever read, so it takes a path on the command
line (`StartleTuningFile.DefaultUserPath` still exists for anyone who wants the old shape), it
matches names case-insensitively, and its `ToJson` exists to seed a starting file rather than to
save state.

**It is loaded per process and is NOT authoritative.** `Gameplay._Ready` applies it before the
world is built. Each peer plays the staging from its own copy, so a server with a 0.8 s tell and a
client at the shipped 0.4 s would burst 400 ms apart. That is stated rather than defended: making
it authoritative means fifteen floats on the round wire for a feel pass. During a tuning session,
pass the same file to both processes — which is exactly what `Run-BurstDoorTest.ps1` does, and it
asserts all three loaded it. See "Open for the orchestrator".

## 3. What happens, in order

`StartleTimeline.Beats` is the whole list, sorted, as offsets from T. On the shipped tuning:

| Beat | At | What actually happens |
|---|---|---|
| `Tell` | T + 0.00 | the task-room lamp drops 40 % and the intercom clicks — **hiders only** |
| `Burst` | T + 0.40 | one frame: blocker off on **every** peer, lamp back up, positional bang at the doorway on every peer, flat bang + camera kick on the hider, and (server) the shove and the flinch |
| `LeafOvershoot` | T + 0.52 | the leaf reaches 125° |
| `KickEnded` | T + 0.70 | the kick is exactly zero |
| `LeafSettled` | T + 0.77 | the leaf is at 110° and the staging is over |

**The list is sorted rather than emitted in a fixed order, and that is load-bearing**: several of
those times are sums of independently tunable knobs, so an overlay can genuinely reorder them (a
0.5 s kick outlasts a 0.12 + 0.25 s leaf) and a consumer walking an assumed-sorted list would fire
the settle before the overshoot. `StartleTimelineTests` pins it.

### The leaf is a tween, and the blocker is the only collision

§5's parenthesis — "a hinge joint can tunnel" — is the reason, and the one thing it would tunnel
through is a player. So `Leaf` is a `MeshInstance3D` with no collider on a `Hinge` empty, and the
only physical fact is `Blocker`, a `StaticBody3D` filling the opening whose collision shape is
**disabled**, never moved and never freed. Freeing it would make the reset rebuild a node the
scene authored (the one thing this level's rules forbid); moving it would sweep a physics body
through wherever the seeker is standing.

**The blocker goes off on every peer, not only the server.** An owner predicts its own movement
against its own copy of the world, so a blocker only the server dropped would be a seeker who
walks through a door their own client still thinks is shut and is then yanked back by the next
reconciliation.

**On the reset the blocker comes back at the END of the 0.6 s close**, not at the start. Nobody is
in the doorway at that moment in practice — the reset edge teleports both players to the holding
room on the same tick — but "in practice" is not "cannot", and the order that cannot trap anybody
costs 0.6 s of an unblocked doorway in an empty room.

### The open leg is thrown, not animated

Quartic ease-out over `LeafOpenSec` to the overshoot, then ease-in-out back to the rest angle.
`StartleTimelineTests.Leaf_ThrowsItselfOutOfTheFrameRatherThanEasingOut` makes the feel claim
measurable: a quarter of the way through the throw the leaf must already be past half its travel.
A linear tween is at 25 % there and reads as a gate opening.

### The camera kick never touches the aim

`FirstPersonCamera.Kick(deg, sec)` sets a transient pitch offset applied **only** where the lens's
basis is written. It never writes `Yaw` or `Pitch`, which is what `FirstPersonIntentSource` puts
into `MoveIntent.AimYaw/AimPitch` — so the replicated aim, the server's aim ray and everything E
resolves against are untouched, and the player does not lose a frame of input. One full decaying
sine over `KickSec`: it starts at zero, throws the view up, comes back *through* zero and ends at
exactly zero. Pitch only and no roll: roll on a first-person lens is the motion-sickness channel
FP-1's whole camera is built to refuse.

### The shove is an impulse, and a Resting prop is WOKEN

`PropManager.ServerBurstImpulse(originGlobal, radiusM, impulseNs)` — server only. Every Loose or
Resting prop inside the radius takes an outward impulse in **newton-seconds**, converted through
that prop's own mass, so a heavy prop is shoved less than a light one by construction. Falloff is
linear (`StartleTimeline.ImpulseNsAt`), clamped at zero — never an inverse square that would fling
whatever is nearest the hinge across the room, and never negative.

**A HELD prop is not touched by the shove.** The flinch is a separate rule with a separate knob;
shoving props out of hands by proximity would take the object off a hider standing two metres from
the door and leave the one four metres away holding theirs, which is a rule nobody could read off
the screen.

### The flinch goes through an existing funnel

`ForceDropOnBurst` calls `PropManager.ScatterHeldBy(hiderPeer)`. That is the existing **public**
funnel that releases into **Loose**; its sibling `ReleaseHeldBy` latches to Resting, which is right
for a disconnect and wrong here — a dropped object has to fall and tumble where everyone can see
it. No new prop lifecycle is introduced by the door. The count is taken before the release and
logged, because "force-dropped what the hider was holding" printed unconditionally reads
identically whether the hand was full or empty.

## 4. The seeker's arrival faces the door — the packet said "verify", and the answer was half

Packet item 3: *"Verify the vestibule teleport lands them facing the door."*

**The BODY does and the LOOK does not.** `RoomTeleport.ServerMove` → `SandboxAvatar.ServerTeleportTo`
rebuilds the avatar's `MoveState` from `MoveState.AtSpawn`, whose yaw is 0; `Vestibule_0` sits on
the door's −Z axis, so a yaw of 0 is precisely "facing the door". But in first person the body
follows the LOOK (`MotorTuning.BodyYawFollowsAim`, FP-1 knob 58) and the look is the local
camera's, which no teleport touches — so within about 83 ms (`AimTurnLerp`) the body swings back
to wherever the seeker happened to be looking in the search room. **Without a fix the seeker can
land with their back to the thing about to open.**

Closed in `BurstDoor.OnPhaseChanged`: on the `-> Together` edge, on the machine whose local
first-person lens belongs to the seeker, the lens is aimed once at the doorway. A **one-shot write
at the instant of arrival** — full control on the very next frame, so it is an arrival pose and
not a cutscene.

**Done by the door rather than by threading a facing through the teleport**, deliberately. The
door is the thing the seeker must be facing and the only node that knows where the doorway is; the
alternative adds a yaw to `RoomTeleport`, to `SandboxAvatar.ServerTeleportTo` and a new replicated
"adopt this facing" signal, and would re-aim **every** room change in the game rather than this
one. If a later lane wants arrival facings generally, that is the shape to build and this line is
the thing to delete.

## 5. The bang

`Sfx.Bang`, **ordinal 24**, synthesised in `SfxLab` like every other member — this foundation
ships no audio assets at all, so there was never a file to reach for. **SFX-1: the next append is
25.**

Three layers summed: a hard broadband crack (the impact, its own 45 ms envelope in absolute
seconds so shortening the tail never shortens the impact), a low sagging 62 Hz body (the mass of
the leaf and the frame taking the load) and a short dark tail (the room answering). A slam, not an
explosion and not a knock; the whole thing is over in 0.34 s. Every number is a named constant
beside `SfxLab.BangPcm`, which is public and returns raw PCM so the Godot-free suite can assert its
arc without an audio device.

It plays twice on the burst: **positional** at the doorway on every peer through `SfxLab`'s pooled
`AudioStreamPlayer3D` path, and **flat** on the hiders' own intercom bus at `BangFlatDb`, because
§5 is right that a positional-only bang is too quiet if the hider happens to be facing away.
Pitch jitter is deliberately **zero** against this palette's own convention: `SfxLab` jitters every
one-shot so repeated footsteps never machine-gun, and this sound happens once per round — a door
that was a slightly different door each time would make the one instant the game is about feel
unreliable.

`SfxLab.PlayUi` gained an optional `bus` parameter so the flat shot can reach the PA chain
(overdrive → 2.2 kHz lowpass → boxy reverb). An unknown bus name falls back to `Sfx` rather than
being assigned, for the reason `PlayStream3D` already falls back: a bus that does not exist yet
makes Godot spam an error per shot and drop the sound entirely.

## 6. The optional knobs, all three off, and what each would need

§5 lists these as "default off for the first ride". They are **declared, validated, overlayable
and read by nothing** — the honest state, and each paragraph below is what turning one on would
actually cost.

**`FakeKnockRatePerMin` (0).** During Seeking, a leaf rattle plus a thud on the hiders' side at
random intervals. The tuning question is not the rate, it is the **distribution**: a Poisson
process at 2/min will sometimes put two knocks four seconds apart, and two knocks in a row teach
the hider that knocks are noise, which is the exact opposite of what the knob is for. It wants
`SparseSfxSchedule`'s shape — a minimum gap plus jitter, which this repo already has unit-tested —
and it must be **server-seeded and broadcast**, not rolled per peer, or the two players hear
different doors and the seeker can hear a knock they did not make. That is one more field on the
round wire or a small reliable RPC of its own, which is the first thing in this packet that would
have to cross the wire.

**`SeekerKnockKey` (false).** A key in the search room that rattles the door remotely. It is a
`IPressable`-shaped verb, so it inherits `INTERACTION-BIBLE` §2/§5 whole: it needs a refusal when
the phase is wrong, a cooldown (a held key must not become a drum roll), and a decision about
whether the hider can tell a real knock from a fake one — which is the actual design question, and
it is Talon's. Cheapest honest version: the seeker's knock and `FakeKnockRate`'s knock are the
**same** sound, so a bluff is possible.

**`SeekerHeatOnIntercom` (false).** A hider-only intercom crackle whose gain follows the seeker's
distance to the target, server-computed and sent as one byte. The tuning is a **curve, not a
gain**: linear distance reads as nothing until the last two metres, and the interesting shape is
probably a floor plus a knee somewhere around the aisle the target is in. It also needs a decision
this packet cannot make — whether it runs during Seeking only (dread) or through `Together` too
(pointless), and whether the seeker can hear their own heat (they must not, or the game tells them
they are warm).

## 8. Two defects found by measuring, not by review

### `PropRegistry` had no Resting → Loose edge at all, and the server's log said "shoved 3"

The first run of the new smoke reported `the best a prop inside the burst radius managed was 0 m`
while the server printed `[door] burst shoved 3 prop(s)`. Both were telling the truth.

`PropRegistry.Release` is explicitly guarded to Held → Loose and **returns false for a Resting
prop** — until the burst door there was no way for anything but a player to move a prop, so the
store simply had no edge for an external force. The shove called `Release`, got `false`, left the
store Resting, and then unfroze the server's own rigid body. `PropManager._PhysicsProcess` streams
only Loose props, so the crate was flung across the room **on the server and nowhere else**, for
the rest of the round.

`PropRegistry.Wake(id, at)` is the missing edge: idempotent from Loose (a second blast reaching the
same tumbling crate is fine), refused from Held (a blast may tumble a crate, never empty a hand
behind the release funnel's back). Four checks in `PropRegistrySelfTest`.

**The general lesson is the one the smoke was written for: measure the prop on a CLIENT's log.**
A server that moves its own copy and nothing else is invisible from the server, and this is the
exact shape of defect the "read the server log *and* the client's" rule in
`.claude/rules/test-suite.md` exists for — one level further along, where the server log is *not*
lying and is still not enough.

### A beat that sums `_Process` deltas fires EARLY by up to one frame

The staging originally accumulated frame deltas from the tick the Found message landed. That
message arrives inside network polling, part-way through a frame, and the next `_Process` hands
over the **whole** of that frame's delta — most of which elapsed before the message existed.

| Run | Configured tell | Measured arm → burst |
|---|---|---|
| headless smoke, 3 peers | 1.200 s | 1.191 / 1.196 / 1.199 s (early by 1–9 ms) |
| **windowed capture client**, whose first post-arm frame also took a screenshot | 1.200 s | **1.070 s — early by 130 ms, 11 % of the beat** |
| after the fix, headless smoke | 1.200 s | 1.203 / 1.205 / 1.212 s |

`Time.GetTicksUsec()` read at the arm is exact at any frame rate. **Read the direction, not just
the magnitude**: a frame-sampled event can honestly only ever be LATE, by less than a frame; an
early one means time is being counted that the event had not happened for yet. Headless it was
invisible, which is the point — the defect was measurable only on the windowed client, which is
also the only client a player ever runs.

Both are in `.claude/rules/test-suite.md`, with the capture-harness measurements that go with the
second.

## 9. Deviations from the packet

1. **`Sfx.Bang` is ordinal 24**, and SFX-1's next append is 25. Told to say it, saying it.

2. **The suite is on udp/7900, not the 7899 the ladder said was free.** VOICE-1's
   `Run-VoiceRoomTest` landed on 7899 from its own worktree first; neither lane could see the
   other, the orchestrator settled it, and the rules file now carries the sentence that was
   missing — *a port is not claimed until it is on `origin`*. Own commit, `00a07f4`.

3. **There is no `TellClickSec` knob**, although §5 says "a 0.2 s click". The click is
   `Sfx.Thunk` on the PA bus, whose recipe is 0.15 s. A knob whose only possible implementation
   was to pitch-shift a fixed buffer to hit a duration is a dial that lies about what it does, and
   a dial that does nothing is worse than an absent one. If the length turns out to matter it
   wants its own `Sfx` member with its own recipe, which is one ordinal and ten lines.

4. **The seeker's arrival facing is written by the door, not by the teleport** (§4 above). The
   packet said "verify"; verifying found half of it broken, and this is the smallest fix that does
   not re-aim every room change in the game.

5. **`PropRegistry.Wake` and `PropManager.Instance` are new public API in another lane's files.**
   Neither was asked for. `Wake` is the defect in §8; `Instance` is the
   `HideSeekDriver.Instance` / `RunDriver.Instance` / `CycleDriver.Instance` idiom this repo
   already uses three times, added because the door lives in the LEVEL and the manager under
   `Gameplay`, and the alternative is a hard-coded relative path that breaks the day anyone
   re-parents a room.

6. **`FirstPersonCamera.Local` is a static.** Same reasoning: the kick is raised by a node in the
   level, exactly one of these exists by construction, and the alternative is walking the whole
   tree once per burst on a path that also runs on a headless server where the answer is always
   null.

7. **`SfxLab.PlayUi` gained an optional `bus`.** Three lines, needed for the flat shot on the PA
   chain, and it changes no existing call site.

8. **The shove's UP component is a fixed fraction (0.35) of the outward push rather than a knob.**
   It is the *shape* of the push and `BurstImpulseNs` is the dial for its strength; a purely
   horizontal shove reads as sliding and a purely radial one from a chest-height doorway drives a
   floor crate into the floor.

9. **The full scene marathon was not run** (§7). The packet's own Gate list does not include it
   and the program assigns it to INT-1 twice over. Twelve reachable suites were run standalone
   instead and the new one is registered so INT-1's marathon picks it up.

10. **The captures are labelled by their measured offsets rather than by the marks that were
    asked for**, and the fourth is `burst + 0.501 s` rather than exactly +0.5. The reason is in
    the rules file: the offset between a bot's `--capture-at` clock and the round's clock is the
    connect time, and it moved by a full second between two runs of one script, so four marks
    computed from a calibration land somewhere else on the next run. The four frames are picked
    out of one 0.25 s grid and timed by their own file mtimes against the door's `wall=` stamps.

11. **The task room's door is authored as a full wall with a flush leaf**, not as a doorway with a
    leaf hung in it — BASE-1's own header asked for that and the reason is unchanged: a hider who
    can see a gap has already been told where the ending comes from.

## 11. Open for the orchestrator

- **The startle tuning is per process and not authoritative.** Two peers with different
  `--startle-file` values burst at different instants. Today that is a tuning-session hazard only
  (pass the same file to both), and the smoke asserts all three processes loaded it. The day a
  knob turns out to matter to *fairness* rather than to taste, it wants to ride the round wire —
  and `TellSec` is the candidate, because a hider with a longer tell than the seeker's server has
  more warning.
- **`Sfx.Bang` is 24; SFX-1 appends at 25.** The two lanes' appends have to be serialised at
  merge and neither may renumber the other.
- **The three anticipation knobs are declared and read by nothing** (§6). Each needs a design
  decision from Talon before it is worth wiring, and `FakeKnockRatePerMin` needs the first new
  field this packet would put on the wire.
- **The bang, the kick and the tell have never been heard or felt by a human.** Every number is
  reasoned and none is playtested. `KickDegrees` 4 and `BangFlatDb` −3 are the two most likely to
  move, and `TellSec` is the one that decides whether the beat is a startle or a warning —
  `--startle-file` exists precisely so Talon can move them between rides without a rebuild.
- **`SearchPillar` is still CARRY-1's disposable fixture and the task room still has no authored
  props.** DOOR-1's own smoke seeds its crates through `--seed-test-props` rather than putting
  content in a room TASK-1 owns. When TASK-1's towers land, the smoke should knock over a real
  tower instead.
- **A capture harness's marks drift by a second between runs** (§7, and the rules file). Any lane
  that needs a frame at a named instant should budget a grid run, not a typed mark.
