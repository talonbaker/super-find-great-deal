## 1. The predicate

**On each client, talker T is on `Pa` iff `RoomOf(T) != RoomOf(local)`; otherwise `Proximity`.**
**On the server, relay T → L unconditionally when `RoomOf(T) != RoomOf(L)`; every same-room pair
still goes through the distance cull.** Both sentences are one function
(`VoiceRouting.IsPa`) reading one room map (`HideSeekDriver.RoomOf`), which is the point: they
cannot drift apart.

Room membership comes from ROUND-1's authoritative teleports, never from sampling positions —
that is ROUND-1's own instruction and there are two reasons for it. The positions are a
*consequence* of the round, so a position-reading resolver disagrees with the round for the frame
between the teleport landing and the next snapshot. And a player standing in a doorway would
**flap**: the PA is a different audio bus with three effects on it, so a flap is not a threshold
wobble, it is the voice audibly switching character mid-word. Phase plus role is a step function
with no boundary to stand on.

| Phase | Hider | Seeker | Anyone else |
|---|---|---|---|
| Holding | holding | holding | holding |
| Hiding | search | holding | holding |
| Seeking | task | search | holding |
| Together | task | vestibule | holding |
| Tally | **unknown** | **unknown** | holding |

**Tally is deliberately unknown and that is not an unfinished branch.** Nobody is moved at the
commit, so where the two of them are depends on which transition arrived there — Together
(task/vestibule), a Seeking timeout (task/search) or a mid-round disconnect (search/holding). In
all three they are in *different rooms*, so the honest "I cannot say" resolves through the
fail-open rule to exactly the route the real geometry calls for, and nothing has to be remembered
to get there. If a later lane needs the literal room at Tally, read the driver's own teleport log
rather than guessing here.

**A peer with neither role is in the holding room in every phase**, because the round moves
exactly two bodies and a third is left where `SupermarketWorld.SpawnPoints` put them. That is a
fact about `OnServerPhaseChanged`, not an assumption, and there is a test that pins it for all
five phases so a lane that starts teleporting spectators has to come and say so.

**Unknown fails open to PA, never to silence.** The PA route is audible everywhere with no
falloff, so an unknown costs one filtered voice somebody did not strictly need; resolving it to
proximity hands the server's cull a 40 m pair and mutes a real player with no log line. Same
direction `VoiceRelayDecider` already fails for an unresolvable position, same reason: the report
a player writes is "I could not hear anyone".

## 2. The change that was not in the packet's shape: the exemption is per PAIR

The gate's PA exemption was resolved **once per packet** — `bool paExempt = PaResolver?.Invoke(sender)`
hoisted above the peer loop. That is correct for what the hook was built for, a broadcast prop:
"T is on the PA" is then a property of T. **It is not a property of T for an intercom keyed on
rooms.** At one instant the same sentence is a PA broadcast to the player two rooms away and
ordinary proximity to the one standing beside them, and a per-talker answer has to pick one of
those for everybody.

So `VoiceManager.PaPairResolver : Func<int,int,bool>?` is new, and on the server it **wins** over
`PaResolver`. With it unwired `RelayGated` is byte-for-byte what it was — every listener gets the
same per-talker answer the hoisted call produced, and the talker's position is still sampled at
most once per packet (now lazily, so a packet every listener is exempt for samples none at all).

Three consequences a reader should know:

- **`--voice-pa-all` now sets BOTH hooks.** It had to. The relay prefers the pairwise one, so a
  blanket per-talker "everyone is on the PA" set on a world whose intercom is wired would be
  silently outvoted and the flag would quietly stop meaning what it says. `Run-VoiceGateTest`
  cell 3 is what would have gone red, eventually, on a world it does not use.
- **`paResolver=wired` is no longer sufficient as a diagnostic.** `LogGateOnce` now prints all
  three hooks, and to stdout as well as to `matchserver.log`. `paResolver=wired
  paPairResolver=NOT-WIRED` on the supermarket is the hazard `VoiceProximityGate`'s header
  describes, one level in — a relay answering "is T on the PA" for the whole match at once.
- **The server still wires `PaResolver`**, as "is T on the PA for *anyone*" — true exactly when
  some other peer is in a different room. It is never more restrictive than the pairwise rule, so
  it can never mute a pair the pairwise rule would have exempted, and it keeps the packet's
  `paResolver=wired` line honest.

The wiring is only applied on a world that has rooms (`_world is SupermarketWorld`). Elsewhere —
the CI slab worlds, `--world open` — no hook is assigned at all and the relay is the build before
this lane, which is what keeps `Run-VoiceGateTest` measuring the gate rather than measuring this.

## 3. The knob

`VoiceConfig.IntercomWetDb`, a **dB trim on the PA reverb's wet mix**, applied when the bus is
built and re-applicable afterwards (`VoiceManager.ApplyIntercomWetDb`). Launch flag
`--intercom-wet-db <db>`, client-side.

**0 dB is exactly what ships.** `WetFromDb(0)` returns `VoiceConfig.PaReverbWet` (0.25) unchanged,
and there is a test that says so — that property is what makes this a trim rather than a retune,
and it means adding the knob cannot have changed the sound. Negative pulls the room off the voice
(-6 dB halves the wet mix, -60 dB is effectively dry); positive clamps at fully wet, because
`AudioEffectReverb.Wet` is a 0..1 mix and past 1 is not a louder room, it is an invalid parameter.

**Wet rather than volume**, because the note it answers is "too muddy for taunting": mud is the
reverb tail smearing consonants, and turning a muddy voice down leaves it a quiet muddy voice. The
overdrive and the 2.2 kHz lowpass are untouched — the character stays, the room comes off.

Talon: `--intercom-wet-db -6` is the first thing to try if a taunt is hard to make out, and
`--intercom-wet-db -60` is "keep the cheap-speaker sound, lose the building".

## 4. The HUD lamp

A third row on `RoundStripWidget`, under the refusal line: **`INTERCOM: <NAME>`** while a voice
from another room is playing on the PA bus, held 0.8 s past the last frame so the gap between two
sentences of one taunt does not read as two different people.

This is `INTERACTION-BIBLE.md` §8.2 and not decoration. §8.2's rule is that a consequence whose
primary channel is audio needs a non-audio one behind it, and here the consequence *is* the
mechanic: the PA route is deliberately filtered and quiet, and a hider who cannot tell whether the
seeker said anything at all is missing the bluff, which is the thing the whole startle hangs on.
It carries the NAME rather than only lighting, because in the program's later N-hider cuts
"somebody is lying to you" and "that one is lying to you" are different facts.

It **reports; it does not gate**. Voice is always on (Talon, 2026-09-19) and nothing in this lane
mutes anyone.

It reads the ROUTE (`VoiceManager.PaSpeakerNow`), not the round — a lamp lit from the phase would
stay lit while the resolver was unwired and the intercom was silent, which is precisely the state
it exists to rule out. Its own row rather than an addition to the phase line: it appears and
disappears mid-round, and a growing line where the eye returns to would make the phase readout
jump. `GameHud.PublishColumn` measures the strip's real height, so nothing below it has to know.

**Not captured headlessly, and that is owed.** A `--bot` client draws no HUD at all, so the same
constraint ROUND-1 recorded as its deviation 9 applies: what the suite asserts is the layer under
the lamp (the route the client resolved), and **a headed capture of the strip with
`INTERCOM: <NAME>` on it is owed**. It needs two windowed clients and a microphone, so it belongs
with Talon's own ride rather than with another headless lane.

### Proved able to fail — twice, and the first one is the whole argument

**Plant A, the client-only wiring** (`PaPairResolver = null`, server `PaResolver = _ => false`) —
the exact hazard `VoiceProximityGate`'s header names:

```
        server: [voice] gate on, paResolver=wired paPairResolver=NOT-WIRED roomResolver=wired
        same room:  talker->ear proximity (rooms holding), ear->talker proximity (rooms holding)
        cross room: talker in task -> ear pa, ear in search -> talker pa, bodies 42.1 m apart
        listener received 384 packets total, 0 in the final 6s
        server relay counters: relayed 639, PA-exempt 0, gated 1001
  - the server reports paPairResolver NOT-WIRED -- ...
  - the listener received only 0 packets in the final 6s at 42.1 m -- the gate is culling the intercom
  - the server's paExempt counter read 0 -- the PA exemption branch never ran ...
  - the server gated 1001 packet(s) -- a cross-room voice must never be culled
VOICE-ROOM TEST OVERALL: FAIL
```

**Read the third and fourth lines of that block.** Both clients' routing verdicts are *perfectly
correct* — every route `pa`, every room right — and not one packet arrived. A suite that asserted
only the route would have passed that build, and the intercom would have been discovered silent
in a playtest. That is why the server's own `paExempt`/`gated` counters, the listener's
final-window delta and the measured 42.1 m separation are all asserted beside the routes.

**Plant B, everything exempt** (both hooks `true`) — the converse, and why the same-room window
exists at all:

```
        same room:  talker->ear pa (rooms holding), ear->talker pa (rooms holding)
        cross room: talker in task -> ear pa, ear in search -> talker pa, bodies 42 m apart
        server relay counters: relayed 1637, PA-exempt 1637, gated 0
  - same room: VoiceTalker routed the other peer as 'pa', expected 'proximity' ...
  - same room: VoiceEar routed the other peer as 'pa', expected 'proximity' ...
VOICE-ROOM TEST OVERALL: FAIL
```

An intercom that "worked" by exempting everything puts a reverb on two people standing face to
face. The cross-room half stayed green through it, which is what shows the two windows are
independent rather than one check wearing two hats.

Both plants were reverted and the suite re-run green on the restored tree.

## 6. What a human should hear in a two-client test

Talon's launcher, two windowed clients, a microphone on each.

- **Holding room, both players standing together.** Clean voice, no filter, no reverb. Walk away
  from each other across the 10 m room: it gets quieter with distance (`InverseDistance`, unit
  size 6 m, hard cutoff 24 m). This is unchanged from the foundation.
- **The instant Start is pressed** — the hider is teleported to the search room 38 m away — the
  other player's voice **changes character mid-sentence**: overdriven, top end gone above about
  2.2 kHz, a boxy room behind it. And it stops getting quieter: walk anywhere in either room and
  the level does not move. That combination, filtered *and* no falloff, is the intercom.
- **`INTERCOM: <THEIR NAME>` appears on the round strip** while they talk and goes out about a
  second after they stop. If you can see the lamp and hear nothing, the relay is culling — that is
  the plant-A failure and the server log's `paPairResolver=` is the first thing to read.
- **Confirm** moves the hider to the task room and the seeker to the search room, 42 m apart
  through two walls. Still the intercom, still no falloff. This is the window the seeker lies in.
- **Nothing ever mutes.** There is no phase in which either player cannot hear the other, and
  there is no push-to-talk change in this lane.
- **If it is too muddy to make out a taunt**, relaunch the clients with `--intercom-wet-db -6` and
  compare; `-60` keeps the cheap-speaker sound and removes the room entirely. 0 (or the flag
  absent) is the shipped character.

## 7. Deviations from the packet

1. **`VoiceManager.GetEmitRouting()` did not exist; it does now.** The packet describes it under
   "What exists". What the tree actually had was `DescribeRouteFor(peerId)` (one peer, a string)
   and `BotHarness`'s per-peer `pa` bool. Built as `GetEmitRoutingVerdict()` (a serialisable
   record) plus `GetEmitRouting()` (its JSON), and the bots log it as `vroute`. It carries the
   ROOMS as well as the routes, which the packet's assertion needs: "both peers say `Pa`" is also
   what two *unknown* rooms produce through the fail-open rule, so a suite reading only the route
   could pass on a session whose round never synced.

2. **The relay's exemption became per (talker, listener) pair, via a new `PaPairResolver`.** The
   packet asks for "relay T → L always when `RoomOf(T) != RoomOf(L)`", which the existing
   per-talker `PaResolver` cannot express. See §2 — this is the substantive design change in the
   lane, and `--voice-pa-all` had to be taught to set both hooks because of it.

3. **`RoomOf(peerId)` was added to the driver, not to the wire.** The packet says "expose
   `RoomOf(peerId)` on the round wire if ROUND-1 did not already". Nothing new goes on the wire:
   the phase and both role ids are already there, absolute, in the one message a late joiner
   receives, and `RoomOf` is a pure function of exactly those. Putting a room table on the wire
   would be a second representation of a fact already replicated, with a way to disagree with it.
   `Gameplay.OnPeerConnected`'s note that "VOICE-1's room membership belongs on these lines too"
   is therefore answered by not needing a line there.

4. **A new suite rather than a copy of the gate suite.** The packet says "a new assertion in a
   copy of the gate suite". `Run-VoiceGateTest` uses `--world open` and three fresh servers to
   exercise on/off/PA-all; the room assertion needs `--world supermarket`, a round driven by
   `--round-script`, and windows selected by phase. A copy would have shared almost no code with
   its original and would have made two files that drift. `Run-VoiceRoomTest.ps1` is its own
   suite, registered last, and `Run-VoiceGateTest` is untouched and still green.

5. **`--intercom-wet-db` was added; the packet only asked for the knob.** A `const` would have
   meant Talon cannot try a value without someone rebuilding for him, which is the difference
   between a knob and a comment. Eight lines in `LaunchOptions`, additive.

6. **The lamp also prints `INTERCOM: SOMEONE`.** The packet specifies "INTERCOM: &lt;name&gt;". A
   display name that has not replicated yet would otherwise remove the lamp entirely at the moment
   it is most wanted; "the intercom is live and I cannot say who" is the half that matters.

7. **`LogGateOnce` prints to stdout as well as to `ServerLog`.** The packet asks the line be
   confirmed; a suite reading `matchserver.log` needs `--log-dir` threaded through, and the
   stdout copy makes the hook state readable from any server log any lane already captures.

## 9. Open for the orchestrator

- **A headed capture of `INTERCOM: <NAME>` is owed**, and it needs a microphone as well as a
  window, so it belongs on Talon's ride rather than on another headless lane. It pairs naturally
  with ROUND-1's owed capture of the refusal sentence — same widget, one screenshot could carry
  both.
- **`--voice-pa-all` now sets two hooks.** Any lane that assigns `PaResolver` on a server must ask
  whether it also means `PaPairResolver`; on a world with rooms, setting only the first is
  silently outvoted. There is exactly one production assignment site (`VoiceIntercom.Wire`) and
  keeping it that way is the cheapest guard.
- **The gate's per-pair exemption costs one delegate call per (talker, listener) per packet**,
  where it used to cost one per packet. At the 6-player cap and 50 packets/s per talker that is
  ~1,500 delegate invocations a second on the server, each of which is two `RoundRooms.RoomOf`
  switches and a string compare — no allocation, no interop, no engine call. It was not measured
  under load because `Run-VoiceGateBandwidth.ps1` measures bytes rather than CPU; if INT-1's
  frame-time numbers move on the server, this is a candidate and the fix is a per-tick room cache
  keyed on the round's sequence number.
- **The intercom is only wired on a world that is a `SupermarketWorld`.** If a later lane adds a
  second roomed world, it must appear in that condition or its voice is proximity-only everywhere.
- **`IntercomWetDb` is Talon's after the first ride.** 0 is the shipped character; the knob exists
  so the answer to "too muddy for taunting" is a relaunch rather than a packet.
