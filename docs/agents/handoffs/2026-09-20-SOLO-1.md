## 1. The solo model, and why it is one sentence rather than a mode

**`--solo` changes exactly one thing: who may hold the two role slots.** With the flag on and
exactly one human present, `HideSeekLoop.FoldFacts` deals that peer both slots. Every edge of the
round then runs *unmodified*:

```
Holding  -- Start   --> Hiding    the one peer to the SEARCH room, with the object
Hiding   -- Confirm --> Seeking   the SAME peer to the SEARCH room  (never the task room)
Seeking  -- found   --> Together  the SAME peer to the VESTIBULE; the door bursts into an
                                  empty task room, sound and all
Together -- End     --> Tally     the card credits BOTH gains to the one peer
Tally    -- 6 s     --> Holding   roles "swap" onto the same peer, reset edge, round two
```

**Nothing was special-cased to make that work**, and that is the design claim worth checking rather
than believing. `CommitTally` reads each role's score back out of the map it has just written, so
one peer holding both roles accumulates `hiderGain + seekerGain` by ordinary arithmetic; the
winner is decided from two totals copied out of the same row, so they are equal, so the match card
is a **draw** — the honest answer when one person played both sides, arrived at without a branch.

**With two or more humans present the flag does nothing at all**, by construction: the solo deal is
gated on `humans.Length == 1` as well as on the flag. A dev server left with `--solo` on plays an
ordinary two-player game the moment somebody joins, which is what keeps this from being a mode.

**It is server-side.** `HideSeekLoop` runs on the server and nowhere else. `Gameplay` pushes a
`GD.PushWarning` when a CLIENT is given the flag, because the alternative is a tester whose solo
game still says TWO PLAYERS ARE NEEDED TO START with nothing anywhere saying why.

### The one thing in the driver that is not "the loop, unmodified"

`HideSeekDriver.OnServerPhaseChanged`'s `Seeking` case decides a destination **per ROLE**. With one
body in two roles that is two destinations for one peer: the task move lands, the search move is
refused inside `RoomTeleport`'s 800 ms per-peer cooldown, and the retry queue fetches the player
back — **the only player in the game spends most of a second in the wrong room, with every phase,
card and score assertion green throughout.** The hider's move is skipped when
`hider == seeker`, and `Run-SoloSmoke.ps1` asserts the negative directly: `task` is never among the
rooms the server named. Generalises to any driver that decides a move per role rather than per
body.

## 2. The waiting room, and the refusal that used to stop the game

> ### RULING (Talon via FABLE_SUPERMARKET, 2026-09-20) — do not re-add "exactly two"
>
> **ROUND-1's "exactly two humans, not at least two" is SUPERSEDED.** A round needs its two ROLE
> SLOTS filled; the number of bodies in the room is not the question. A third or later player
> waits, and **a suite that finds a three-player Start refused is reporting a regression, not a
> guard.** `NeedTwoPlayers` is not gone — it still fires for fewer than two, which is the case
> that mattered. The assertion that replaces the deleted three-human refusal is the **WAITING
> row** in `Run-HoldingBoardTest.ps1`. Same words are in `.claude/rules/test-suite.md` so this
> does not have to be rediscovered from a handoff.

**ROUND-1 required EXACTLY two humans to Start**, and a third body in the holding room refused the
round for the two who were playing. That is not a hypothetical: `Capture-HoldingBoard.ps1`'s own
header records losing a whole run to it —

```
[round] refused: NeedTwoPlayers - TWO PLAYERS ARE NEEDED TO START (phase=Holding humans=3)
```

— and concludes "a capture script for this game gets two windows, no more". Talon's second
sentence reverses the rule, so the gate now asks **whether both role slots are filled**, not how
many bodies are in the room:

```csharp
if (s.HiderPeerId == 0 || s.SeekerPeerId == 0
    || (s.HiderPeerId == s.SeekerPeerId && !t.Solo))
    return s with { Refusal = HideSeekRefusal.NeedTwoPlayers };
```

Read it in all three cases: **one human** on a shipping launch has no seeker id, so
`NeedTwoPlayers` still fires exactly as it always did; **two** fills both distinctly; **three or
more** fills both from the first two by join order and the rest hold no role. The same-id clause is
the whole of `--solo` at this branch.

### What a waiting player gets

- **A score row**, at zero, from the first tick they are present (`FoldFacts` already did this).
- **A board row reading `WAITING`** where HOLD-1 printed `—`. The dash was a true statement
  answering the wrong question: the reader wants to know *am I in this game*.
- **A status line under the rows** — `1 WAITING · NEXT FREE SEAT IS YOURS` — because "WAITING" with
  no exit written beside it is `INTERACTION-BIBLE.md` §5 one level up from a button: it names the
  state and not the thing to do about it. It shares the overflow label rather than taking a new
  one (see deviation 3).
- **Voice, unchanged.** `RoundRooms.RoomOf` already answered `HoldingRoom` for a peer with neither role, and
  `VoiceIntercom` routes it by proximity, which is what "they can hear and talk" already meant.
- **All three buttons refused by name**, with `PressRefusal.NotInThisMatch` and the sentence
  `YOU'RE UP NEXT ROUND — WAIT HERE`, and all three lamps Dark so they are told *before* they press
  as well as after.

### How the wait ends — and what "dealt in" actually means here

**The existing `Holding` role repair already does it**, which is why this packet adds no selection
logic at all. The repair fires whenever the pair is invalid — a role holder who has left, a stale
id, a solo pair once a second person arrives — and refills both slots from the live roster in join
order. So **a waiting player is dealt in the moment a seat opens**, which is at worst the next
round and never mid-round.

The packet's ruling says "dealt in on the next match start … the first two by peer id who are
present". That is deviation 2 below: the outcome is the same or better and the cost of the literal
rule was a change nobody asked for.

## 3. `PressRefusal.NotInThisMatch`, and the number space the two enums share

`RoundButtonRules.Gate` answers a waiting player **before** the per-kind rules, so all three
buttons say the same true thing:

```csharp
if (hiderPeerId != 0 && seekerPeerId != 0 && presserPeerId != 0
    && presserPeerId != hiderPeerId && presserPeerId != seekerPeerId)
    return PressRefusal.NotInThisMatch;
```

Neither existing reason would do. `NotNow` is a lie — the phase is right. `NotYourButton` is the
hider/seeker distinction, a different fact about somebody who *is* playing.

**The guard is on both roles being dealt**, so a round with vacant slots excludes nobody. Without
that, a peer that has simply not synced gets a dead button with a confident wrong reason on it,
which is worse than a dark one.

**The lamp agrees** (`RoundButtonRules.InThisMatch`), and `LampFacts.HumanCount` was **removed**
rather than left unread: the START lamp was its only reader, as `HumanCount == 2`, and that
condition put the lamp out for both players the moment a third person walked in — and would have
put it out for a solo tester too.

## 4. Deviations from the packet

### 1. `NotInThisMatch` is **not** mirrored into `HideSeekRefusal`, and the mirror would have been a bug

The packet says "a new `PressRefusal.NotInThisMatch` mirrored in `HideSeekRefusal`". Two reasons it
is button-only:

- **The loop could not produce it.** `HideSeekLoop` never learns who pressed. `HostPressedStart` is
  an OR across every registered `IRoundFactSource` (ROUND-1's rule, so the dev script can add a
  press and never swallow one), so there is no presser identity at that branch to refuse. A mirror
  would be a dead enum member.
- **The two enums share ONE number space and 5–7 are already the button's.** `RoundButtonText`
  maps the round's reasons across with `(HideSeekRefusal)(byte)refusal` — an identity map,
  deliberately, so there is exactly one list of refusal sentences in the game. A round refusal
  numbered 5 would be rendered on the wire as `WAIT — THIS ROUND IS STILL RUNNING`, which is
  precisely the "a stale peer renders a different sentence than the server refused with" hazard
  ROUND-1's own handoff says the stable ordinals exist to prevent.

`PressRefusal.NotInThisMatch = 8` (append-only), and
`SoloRoundTests.ThePressRefusalOrdinals_MirrorTheRoundsAndKeepTheButtonsOwnRangeClear` **fences
both halves** — every `HideSeekRefusal` value maps to the identically-named `PressRefusal`, and no
`HideSeekRefusal` member has entered 5+. That invariant was previously written down and not
enforced; it is enforced now.

### 2. The pair is chosen in JOIN order, not "the first two by peer id"

The packet's ruling says the next match's two players are the first two **by peer id** who are
present. Not adopted:

- **It would silently change which of two players hides first in every ordinary session.** Roles
  are dealt from the roster in join order — program §1 item 5, "the host hides first" — and peer
  ids are random ENet numbers. Switching the ordering makes who-hides-first a coin flip and turns
  `HideSeekLoopTests.FirstRound_TheHostHides_AndTheSecondJoinerSeeks` into a lie. Nobody asked for
  that, and it is not what the ruling is about.
- **The visible outcome is identical, and arrives sooner.** "First two by peer id" never rotates
  either — a third player with the highest id would wait forever under both rules, which is the
  packet's own "no 3+-player round logic beyond waiting". What the ruling is really about is a
  player who joined while a match was running: they do not disturb it, and they take a seat as soon
  as one is free. The existing repair does that **at the next round**, not merely at the next match
  start.
- **The board reads correctly either way**, because the WAITING row is derived from the two role
  ids on the wire rather than from any ordering.

Reversible in one line in `FoldFacts` plus one test if the orchestrator wants the literal rule.

### 3. The waiting line is on the board's STATUS line, not its FOOTER

The packet says "say so on the board footer". The footer is the last **card** — `BoardFooter`, a
fact about a round that has finished — and `HoldingBoardTests.TheFooterFloorIsBelowTheWorstLineThe
WireCanProduce` already measures it shrinking to `MinScale` (0.30) on the longest line the wire can
produce. A second clause on it would make the result of the match unreadable in order to say
something about the room.

`WAITING` is a fact about the **rows**, so it went on the small line that sits with them — the one
HOLD-1 already used for `+N MORE`, now `HoldingBoardModel.StatusLine`, which composes both. **No
new `Label3D`**, which matters: a new node in `HoldingBoard.tscn`'s prefab is exactly what
`SupermarketWorldSelfTest`'s packed-vs-live count exists to catch (HOLD-1 paid for that once
already).

### 4. `Run-SoloSmoke.ps1` is a new suite rather than an extension of `Run-RoundLoopSmoke.ps1`

The packet allows either. Separate, because the gate also says "the normal smoke unchanged": the
two prove different things and a run that could not tell you which half failed would be worth less
than either. `Run-RoundLoopSmoke.ps1` is byte-identical to its base.

### 5. `HoldingBoardModel.NoRole` was RENAMED to `Waiting`, not kept beside it

Two constants for one cell is two things that can disagree on a wall two people are reading. The
old name has no other callers (grepped across `**/*.cs`, `**/*.ps1`, `**/*.tscn`).

## 6. How Talon plays solo

Two terminals, one window. `--solo` goes on the **server**; the client needs nothing.

```powershell
cd C:\repos\sfgd-ride
dotnet build SuperFindGreatDeal.sln

# terminal 1 -- leave it running
Godot_v4.7-stable_mono_win64_console.exe --headless --path . -- --server --port 7777 --solo

# terminal 2 -- this is you
Godot_v4.7-stable_mono_win64_console.exe --path . -- --windowed --name Talon
```

In the client: **Join -> Direct Connect -> `127.0.0.1:7777`**. No Steam, no `--world` (the
supermarket is the default), no `--round-script` -- every beat below is a real button or a real
object in your hands.

Then, alone:

1. **Holding room.** Take something off the rack. The START button lights. Press it.
2. **Search room.** You are the hider. Hide the object anywhere a hand could get it back out, put
   it down, press **I'M DONE HIDING**.
3. **Search room again.** You are now the seeker, in the same room, and the task room is empty.
   Find the thing that does not belong and put it in the drop-off bin.
4. **The burst.** The door bangs open and you are in the vestibule. Walk through into the empty
   task room and press **END ROUND**.
5. **Tally, then again.** Round two, then a match card. It reads **DRAW** -- both totals are your
   own, so there is nobody to beat; see the last bullet of §8.

**Engine flags before the bare `--`, game flags after.** A game flag on the wrong side is
swallowed and looks exactly like a hang. And the flag belongs on the SERVER: on a client it prints
a warning and does nothing, because the loop only runs server-side.

## 7. The bible check

```
Bibles applied:  MECHANICS (the loop resolves its own state, timers and scoring, and this packet
                 changes who may hold its two roles);
                 INTERACTION (a third player walks up to three in-world buttons and every one of
                 them owes them an answer).
                 LEVEL does not apply — nothing is arranged, no geometry is added, and the one
                 board change is text in a Label3D that already exists.
Items checked:   MECHANICS §2 (test-and-set in one branch — the Start gate reads the two role ids
                 the same fold wrote this tick, so there is no window between observing the pair
                 and accepting on it); §4 (idempotence — the solo deal is a pure function of the
                 roster and the flag and is re-derived every Holding tick to the same answer, and
                 the board's WAITING is a function of one absolute message, so a late joiner and
                 a peer that was there paint the same wall); §6 (define the extremes — zero
                 humans, one human with the flag and without it, two, three, five past the board's
```
