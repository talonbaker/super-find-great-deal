## 2. The defect the merge produced rather than inherited

**Three lanes off one base all shipped a new suite on udp/7896.** ROUND-1, FP-1 and CARRY-1 each
read the same `Run-CarryNetTest` 7893/7894/7895 ladder and computed the same "next free" port, and
none could see the other two. The merge appends all three near the end of `Run-AllTests.ps1`'s
registry, so in a marathon they run back to back on one socket.

Measured, not reasoned — the first post-merge run of `Run-FirstPersonTest.ps1`, immediately after
`Run-RoundLoopSmoke.ps1` released 7896:

```
[1/3] launching dedicated server on udp/7896...
FAIL: the server never reported listening within 30s; see tests/logs/fp-server.out.log
```
```
ERROR: Couldn't create an ENet host.
... [server] failed to start server port=7896 transport=enet err=CantCreate
```

**This is not the port contention the rules file already excuses.** FP-1's own handoff records a
udp/7777 collision with a sibling worktree's Godot and correctly calls it contention rather than a
red. The discriminator is whose process holds the socket: contention is another worktree's and
clears on a re-run; this is two entries of one registry and would have failed every marathon
identically.

Fixed in two commits (`2d74706`, `58649b7`): ROUND-1 keeps 7896 — it documented the claim in its
own header, its handoff and the rules file — FP-1 moved to **7897**, `Run-PlaceTest` to **7898**.
Every port in `tests/` was audited afterwards: **27, all distinct.**

### 3.1 A first-person camera through a ROUND-1 teleport — PASS

ROUND-1's teleports move a player 40–80 m between rooms on the server; FP-1 mounts the player's
camera as a child of the avatar. ROUND-1's own smoke drove that with third-person bots.

**Nothing in a bot's log could see a camera**, which is why this needed instrumentation before it
needed a check: `BotHarness` logs `Peers[]`, a list of avatar-node positions, so a lens that had
gone stale, been unparented or gone NaN across a teleport reads there as a perfectly healthy body
standing in the right room. Two additions (`6850fd6`), both read-only:

- **`Sample.Lens`** — this peer's own lens in world space, plus `Off` = |avatar origin → lens|,
  which is the eyeline and nothing else, so it must hold its value through a room change. Null,
  not zeroed, when the process built no rig.
- **`SandboxAvatar.TakeCommandedTeleports()`** and the `Tp`/`Tj` columns — a take-and-reset count
  of epoch bumps the OWNER consumed, counted inside `Reconcile`'s `teleported` branch where the
  bump is actually spent. `LastCorrectionM` cannot answer this: a bot samples at ~5 Hz and
  `Reconcile` runs at 60, so the ordinary sub-centimetre corrections have already overwritten a
  teleport's by the time anything reads it. The distinction matters — a room change that arrived as
  an ordinary large correction moves the body just as far and is a body the owner *interpolated*
  into rather than snapped to.

### 3.2 Rotate-held against the first-person camera — PASS

CARRY-1's `HeldPropRotator` reads the mouse in `_Input` and calls `SetInputAsHandled`; FP-1's
`FirstPersonCamera` reads it in `_UnhandledInput`, which runs afterwards and only for events nobody
consumed. CARRY-1's own header wrote that down as an **assumption** about "any camera that also
reads the mouse as unhandled input" and flagged it for this merge.

Measured with a new probe, `--rotate-look-selftest`, which builds a real rotator on a `--bot`
avatar through the shipped `HeldPropRotator.Attach` — the same pattern `--first-person-cam` already
uses for the camera — and injects the *same* synthetic mouse motion twice:

```
[rotlook-selftest]   rotate held:     prop turned 2.0000 rad, camera yaw moved 0.0000 rad
[rotlook-selftest]   rotate released: prop turned 0.0000 rad, camera yaw moved 0.5000 rad
[rotlook-selftest]   5 synthetic motion event(s) of 40 px per pass, identical in both
[rotlook-selftest]   rotator reported Active=True while the modifier was down
[rotlook-selftest] SUMMARY failures=0 result=PASS
```

`2.0000` is exactly `5 x 40 px x 0.010 rad/px` and `0.5000` is exactly `5 x 40 px x 0.0025 rad/px`.
**With RMB held the prop turns and the view does not; on release the view turns and the prop does
not.** No fix needed.

**Each half is the other's positive control, and that is the point.** If the rotator consumed
motion it should not, the player's view would simply stop working after the first time they turned
something — and the "prop rotates, view does not" half would still pass.

**One trap found while building it, and it is in the rules file now.** The first run was headless
and printed `0.0000 rad` on all four quantities, failing two checks **including both positive
controls**. That was not a routing failure: `Input.MouseMode = Captured` is silently refused by the
dummy DisplayServer in a headless run, and both rigs correctly gate on a captured cursor, so the
probe measured two rigs that had each correctly decided to do nothing. The probe now names that
case itself. It is also why this is a one-off integration check and not a registered suite — it
takes the real cursor for the length of its run, which `Run-FirstPersonTest.ps1` deliberately
refuses to do.

### 3.4 A held prop is never on the first-person hidden layer — PASS

FP-1 hides the local body by putting its whole visual rig on render layer 19 and dropping 19 from
the lens's cull mask. A carried prop on that layer would vanish from the hands of the person
carrying it — and only for that person.

**Static half.** Layer 19 is written in exactly one place in the tree: `AvatarVisual.HideSubtree`,
reached only from `HideFromFirstPerson`, which walks only the `AvatarVisual` subtree. Nothing
reparents a prop into an avatar — `NetworkedProp.AddChild(Body)` adds the prop's own body to the
prop, and no `Reparent` call outside `AvatarVisual`'s own rig assembly exists. The blob shadow is a
top-level quad and is deliberately not hidden (FP-1's reasoning, unchanged).

**Runtime half, and it is a mask query rather than a photograph** — a photograph cannot tell
"culled" from "out of frame", "behind a wall" or "clipped by the near plane", and the near plane is
a live hazard here (3.3):

```
[rotlook-selftest]   held prop 1000: 3 renderable(s), 0.650 m from the lens (near plane 0.05 m),
                     lens cull mask 0xBFFFF, first-person hidden layer 19 (bit 0x40000)
```

`0xBFFFF` has bit `0x40000` clear — layer 19 dropped, as designed — and **none of the held prop's
three renderables is on layer 19, and every one of them shares a layer with the cull mask.** There
is a positive control: a prop with no renderables at all would pass both assertions while proving
nothing, so the count is asserted first.

**Photograph.** `docs/qa/2026-09-19-int-0/FpCarry-13s.png` — one windowed `--first-person-cam` bot,
no other client in the session, lens pitched 30° down onto its own hands. The gold mass across the
bottom of the frame is the held crate (prop 1000, 0.268 m from the lens at that instant); the
highlighted box with the `E` chip further in is prop 1003 on the floor at 0.899 m, which is what
the aim ray is resolving against. Both are from the log, not from the pixels.
