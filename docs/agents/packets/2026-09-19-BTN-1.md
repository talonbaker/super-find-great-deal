## Why this packet is small on purpose

Talon: prior in-game buttons did not work well; this MVP needs simple, reliable button-based
interaction — basic, not a custom system, but it has to actually work. The one shipped control in
the foundation failed three playtests: a debounce mistaken for a confirmation, a sign hidden behind
the player's own third-person body, a prompt that never said which key. First person removes the
second. You remove the other two by construction.

## Build

### `RoundButton` (one class, three instances, authored in the room scenes)

A `StaticBody3D` with a base, a cap that physically depresses 4 cm on press, a lamp that shows state
(`Lit` = will accept a press right now, `Dark` = will refuse, `Pressed` flash), and a `Label3D`
naming it ("START", "I'M DONE HIDING", "END ROUND"). Implements `IPressable` (group `pressable`,
`PressRadiusM` 1.6). `Press()` on the client **asks**: `RpcId(1, RequestPress, buttonId)`. The server
adjudicates through ROUND-1's facts — the button does not hold logic; it sets the fact
(`HostPressedStart` / `HiderPressedConfirm` / `AnyPressedEnd`) and the loop answers with either a
transition or a refusal reason on the next step. The server broadcasts `ApplyPressResult(buttonId,
peerId, accepted, reason)` reliable + CallLocal; every peer animates the cap; the presser
additionally hears a click (accepted) or a dull thud + a 0.15 s shake (refused) and sees the reason
text via the HUD strip for two seconds. **A press with no visible/audible result on the presser is a
defect.** No debounce anywhere: the loop's one-shot fact reading is the idempotence.

The lamp state is derived every 100 ms on each client from the wire (phase + role + humans): e.g.
START is Lit only in Holding with two humans and the hider holding a rack object. This is the
affordance: a Dark button tells you not to bother before you press it, and the reason text tells you
why when you do anyway.

Live key glyph via `InteractPrompt` + `ControlGlyphs` when the button is the pick target; the label
never hardcodes "E".

Placement: START in the holding room beside the rack; CONFIRM in the search room by the exit wall;
END in the task room beside the burst-door wall. Authored `.tscn` per room section.

### `DropOffBin` (search room)

An open-top box (authored, static walls) with an `Area3D` sensor inside. The **server** watches
body-entered for `NetworkedProp` bodies: the target prop id → sets ROUND-1's `TargetInDropOff`
fact once, lamp goes green, a chime on every peer; any other prop → a buzz on the seeker only and
the lamp flashes red for 0.5 s (the prop stays where it fell — no ejection). Clients never decide.
Target id comes from the `ObjectRack` fact below, via the round wire.

### `ObjectRack` (holding room)

Three authored near-miss props on a shelf (red sphere, red cylinder, red wedge; same size class as
the search room's red cubes — SHELF-1 owns the cubes, you author these three as `NetworkedProp`s
adopted by `PropManager`). The server folds `HiderHeldRackProp` = "the hider currently holds one of
these three ids", and on the Holding → Hiding transition records **that** id as `TargetPropId` on
the wire (ROUND-1 exposes a setter or you extend the fact source — say which). The other two stay on
the rack; the seeker can look at the rack during Hiding and knows the shape (the brief: both players
know what they are looking for).
