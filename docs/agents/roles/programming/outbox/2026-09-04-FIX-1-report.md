## Decisions made (with why)

**1. The mechanism: one absolute exit moment for all three bots, derived from the server's
announced schedule.** The packet offered three shapes and left the pick to me. I took the middle
one — a duration derived from the reset schedule — because it is the only one that needs no new
`BotHarness` flag (out of my paths) and no process-killing (which would break the existing
"exited with code 0" check). Concretely: the server prints `resetLandsAt` at the frame its clock
starts; the runner records that moment as session zero, adds `$PostResetSettleSec`, and hands each
bot `session end − its own launch offset` as `--duration`. All three name the same wall-clock
moment. Moving `--bubble-reset-at`, `BubbleResetConfirm.MinDwellSec` or `ConfirmWindowSec` now
moves every sampling window with it.

**2. `$PostResetSettleSec = 6` — a value fork, taken.** It is the only free number left in the
schedule, and it is a *margin*, not a mark. At the measured 4.9 Hz sample rate that is ~29
post-reset samples on every peer where assertion 8 needs one. Large enough that boot skew, a slow
flush of the server's schedule line and a late broadcast together cannot eat it; small enough that
the suite stays near its historical ~40 s (measured after: 38.25 s session, same order as the old
36 s).

**3. `BubbleSelfTest.ConfirmDelaySec` made public and printed.** The reset does not land at
`--bubble-reset-at`; it lands `ConfirmDelaySec` later, because the lever is a two-stage press. A
runner that retyped 2.25 would have been a *third* independent copy of a timing that already has
two — exactly the trap the fixture's own comment at `:72-74` warns about. Announcing it is the
smallest change that makes the derivation real. This is the fixture's timing and nothing else.

**4. Assertion 8 names the HARNESS, deliberately.** Per NET-1 §11.2 rule 3, a window that closes
early must fail as *"the late joiner's sampling window CLOSED Xs BEFORE the reset … this is a
HARNESS defect, not a replication one, and every late-joiner reset assertion below it is
VACUOUS"* — never as "the broadcast never arrived". That distinction is the whole packet.

**5. Assertion 6 was not weakened, and neither was anything else.** The old failure string
(`C (late) never saw the reset return the tally to 0 and every bubble to visible`) is byte-for-byte
unchanged. Assertion 8 sits *beside* it, so a genuine replication defect would fire 6 alone and a
harness regression would fire both.

**6. A's and B's windows had the same latent defect — stated, as the packet asked.** 36 s typed
against a reset landing at 32.25 s is 3.75 s of margin, held by a number that did not move when
`ResetAtSec` did. Same class, currently winning the race instead of losing it. They are derived
now too, from the same line.

(NET-1 §11.3).** The derivation here reads the schedule off a *log line*, which costs one

written from scratch would be cleaner with one absolute mark handed to every bot and no arithmetic
in PowerShell at all. `scripts/game/BotHarness.cs` is outside FIX-1's paths so I did not build it;
it is a small, obviously-correct change if a courier-harness packet wants it.
